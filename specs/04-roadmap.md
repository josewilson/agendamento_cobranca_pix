# Roadmap

## Entregue

- **Fase 0 — Setup**: projeto Spring Boot 3.5.11 + Java 21, dependências (web, data-jpa, validation, postgresql, flyway, testcontainers, archunit, wiremock), `docker-compose.yml` com Postgres local.
- **Fase 1 — Domínio**: entidades, value objects, máquina de estados, `VerificadorDeConflito`, exceções de domínio. Testes unitários puros (sem Spring). Ver `01-dominio.md`.
- **Fase 2 — Casos de uso + adapters em memória**: as 7 portas de entrada, portas de saída, eventos de domínio, adapters em memória (repositórios, gateway de pagamento fake, publicador de eventos, clock real). `ArchitectureTest` (ArchUnit). Smoke test do contexto Spring completo em memória. Ver `02-casos-de-uso.md`.
- **Fase 3 — Persistência real + API REST**: entidades JPA, mappers, migrations Flyway, repository adapters PostgreSQL, testes de integração com Testcontainers (pendente de execução — requer Docker Desktop rodando neste ambiente), troca de adapter em memória ↔ PostgreSQL via `@Profile("dev")`/`@Profile("!dev")`. Controllers REST + DTOs + `GlobalExceptionHandler`, testados com `@WebMvcTest`. Ver `03-api-rest.md`.
- **Fase 4, item 1 — Gateway de pagamento Pix real (Asaas)**: `AsaasGatewayAdapter` (`@Profile("!dev")`) integra de verdade com `api-sandbox.asaas.com/v3` — cria o cliente no Asaas, cria a cobrança Pix (com `agendamentoId` como `externalReference`) e busca o QR Code. `AsaasWebhookController` (`POST /api/webhooks/asaas`) recebe a confirmação real, validando o header `asaas-access-token` contra `asaas.webhook-token`. Testado com WireMock (adapter) e `@WebMvcTest` (webhook), sem chamar a API real. Config em `asaas.*`, chave/token lidos de `ASAAS_API_KEY`/`ASAAS_WEBHOOK_TOKEN` (vazios por padrão — a aplicação sobe normalmente sem eles, só não consegue emitir cobranças reais). A porta `GatewayDePagamento` ganhou o parâmetro `Cliente` (necessário para criar o cliente no Asaas) — mudança que se propagou para `GatewayDePagamentoFake` e `CriarAgendamentoService`. Ver `02-casos-de-uso.md` e `03-api-rest.md`.
- **Fase 4, item 3 — Scheduler de expiração**: `ExpiracaoReservaScheduler` (`adapter/in/scheduler/`) aciona `ExpirarReservasPendentesUseCase` periodicamente via `@Scheduled`, intervalo configurável em `agendamento.expiracao.intervalo-ms` (padrão 60s). Usa `initialDelay` igual ao `fixedDelay` para não disparar no instante em que qualquer teste sobe o contexto Spring completo. Testado isoladamente (chamada direta ao método, sem depender do agendador do Spring). Ver `02-casos-de-uso.md`.
- **Fase 4, item 3 — Notificações multicanal (canal e-mail)**: porta `EnviadorDeNotificacao` + `NotificacaoDispatcher` (roteia por `CanalNotificacao`) + `NotificacaoEventListener` (`adapter/in/evento/`, reage a `AgendamentoCriado`/`AgendamentoConfirmado`/`AgendamentoCancelado` via `@EventListener`, falhas de envio só logadas, nunca propagadas). `PublicadorDeEventosSpring` (`@Profile("!dev")`) passou a delegar ao `ApplicationEventPublisher` do Spring para o listener conseguir reagir de verdade — antes só existia a versão em memória que apenas acumulava eventos sem nenhum consumidor. `AgendamentoConfirmado`/`AgendamentoCancelado` ganharam o campo `clienteId`. Canal real implementado: `EmailEnviadorDeNotificacao` (`@Profile("!dev")`, SMTP via `JavaMailSender`, testado com GreenMail). `SMS` e `WHATSAPP` existem no enum `CanalNotificacao` mas sem adapter real ainda — ver pendências abaixo. Ver `02-casos-de-uso.md`.
- **Fase 4, item 1 — Segundo gateway de pagamento (Mercado Pago)**: `MercadoPagoGatewayAdapter` + `MercadoPagoWebhookController`, ativos só quando `pagamento.gateway=mercadopago` (`@ConditionalOnProperty`, `AsaasGatewayAdapter`/`AsaasWebhookController` viraram o padrão explícito com `matchIfMissing = true`). **Essa é a demonstração real de troca de gateway via configuração** que o projeto persegue desde o plano inicial — nenhuma linha de código de aplicação ou domínio muda, só a propriedade `PAGAMENTO_GATEWAY`. Integração propositalmente diferente da do Asaas, preservando o que cada gateway realmente exige (registrado como comentário na classe): sem "criar cliente" separado (dados do pagador vão direto no corpo), JSON em snake_case, webhook que só traz o id do pagamento (não o status — precisa de uma segunda chamada, `consultarPagamento`), assinatura HMAC-SHA256 no header `x-signature` em vez de token simples. Config em `mercadopago.*`, testado com WireMock (adapter) e `@WebMvcTest` (webhook, incluindo validação de assinatura válida/inválida). Ver `02-casos-de-uso.md` e `03-api-rest.md`.
- **Fase 4, item 3 — Sincronização com Google Calendar**: `CalendarioExternoPort` (`sincronizarEvento`/`removerEvento`) + `CalendarioEventListener` (`adapter/in/evento/`), reagindo só a `AgendamentoConfirmado` (cria o evento) e `AgendamentoCancelado` (remove) — propositalmente não reage a `AgendamentoCriado`, já que um agendamento pendente de pagamento pode expirar sem nunca ocupar a agenda de verdade. `GoogleCalendarAdapter` (`@Profile("!dev")`) autentica via conta de serviço (`com.google.auth:google-auth-library-oauth2-http`, sem fluxo OAuth2 interativo) e chama a API REST do Google Calendar diretamente (mesmo estilo dos gateways de pagamento — sem SDK pesado). O id do evento no Google é derivado deterministicamente do `agendamentoId` (hex do UUID sem hífens), dispensando um mapeamento à parte. Testado com WireMock, inclusive o próprio token server (`google-calendar.token-server-uri`, redirecionável para o WireMock em teste — a lib assina o JWT localmente com uma chave RSA descartável gerada em memória, nunca validada pelo WireMock). Config em `google-calendar.*`, credenciais vazias por padrão (a aplicação sobe normalmente sem elas, só não sincroniza de verdade). Ver `02-casos-de-uso.md`.
- **Demonstração via browser (Swagger UI)**: adicionado `springdoc-openapi-starter-webmvc-ui`, expondo `/swagger-ui.html` para exercitar a API REST interativamente. `DevDataSeeder` (`adapter/in/seed/`, `@Profile("dev")`) popula prestador/cliente/serviço de IDs fixos no startup, só para permitir testar `POST /api/agendamentos` pelo Swagger sem precisar de endpoints de cadastro (fora do escopo deste projeto). Nessa investigação ficou claro que o perfil `dev` só trocava os adapters de negócio — Flyway/DataSource/JPA continuavam ativos e a aplicação real (fora dos testes, que já excluíam essas auto-configurações manualmente) não subia sem Postgres. Corrigido com um documento de perfil dedicado em `application.yml` (`spring.config.activate.on-profile: dev` excluindo `HibernateJpaAutoConfiguration`/`DataSourceAutoConfiguration`/`DataSourceTransactionManagerAutoConfiguration`/`FlywayAutoConfiguration`), removendo a exclusão duplicada que só existia em `AgendamentoApplicationTests`.

## Pendente — Fase 4 (demais integrações, uma por vez)

1. **Execução de estorno no cancelamento** — hoje `CancelarAgendamentoUseCase` retorna `ResultadoCancelamento` mas não aciona nenhum reembolso real; isso depende de decidir como referenciar a cobrança original a estornar em cada gateway.
2. **Canais WhatsApp e SMS** — a porta `EnviadorDeNotificacao` e o `NotificacaoDispatcher` já suportam múltiplos canais (é só registrar um novo `@Component` por canal); falta implementar os adapters reais (ex.: Twilio, Z-API) e decidir por qual canal cada evento deveria notificar (hoje `NotificacaoEventListener` só usa `EMAIL`).

## Debito tecnico conhecido

Os 4 testes `*RepositoryAdapterIT` (Testcontainers) nunca haviam rodado de fato nesta maquina por falta de Docker Desktop. Agora que ficou disponivel, todos os 4 rodaram pela primeira vez e **todos falharam**, revelando 3 bugs latentes da Fase 3 — nenhum causado pelo trabalho desta sessao:

1. **Sem isolamento entre testes da mesma classe** (`AgendamentoRepositoryAdapterIT`, `ClienteRepositoryAdapterIT`, `ServicoRepositoryAdapterIT`): os metodos `@Test` de cada classe compartilham o mesmo container Testcontainers sem rollback transacional entre execucoes, entao o `Prestador`/`Cliente` de CPF/CNPJ fixo inserido no `setUp()` viola a constraint unica (`uk_prestador_documento`/`uk_cliente_documento`) a partir do segundo teste da classe.
2. **`Instant` comparado por igualdade direta** (`AgendamentoRepositoryAdapterIT.deveSalvarEBuscarAgendamentoPorId`): o valor em memoria tem precisao de nanossegundos, o lido de volta do Postgres (`timestamp`) foi truncado para microssegundos — `assertEquals` falha por divergencia de precisao, nao por bug de persistencia.
3. **`BigDecimal` comparado por igualdade direta** (`PrestadorRepositoryAdapterIT.deveSalvarEBuscarPrestadorPorId`): `percentualRetido` volta do Postgres (`numeric`) com escala diferente (`100.00` vs `100` em memoria) — `BigDecimal.equals()` é sensível a escala mesmo quando `compareTo` é zero.

Nenhum destes é um bug do adapter de persistência em si (os dados estão corretos no banco); são problemas dos próprios testes (falta de isolamento, comparação ingênua de tipos sensíveis a precisão/escala). Correção sugerida para quando essa frente for retomada: `@Transactional` na classe de teste (rollback automático) ou truncar as tabelas em `@AfterEach`; comparar `Instant` truncado para microssegundos ou com `isCloseTo`; comparar `BigDecimal` via `compareTo`/`isEqualByComparingTo` em vez de `equals`.
