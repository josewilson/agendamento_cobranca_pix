# Roadmap

## Entregue

- **Fase 0 — Setup**: projeto Spring Boot 3.5.11 + Java 21, dependências (web, data-jpa, validation, postgresql, flyway, testcontainers, archunit, wiremock), `docker-compose.yml` com Postgres local.
- **Fase 1 — Domínio**: entidades, value objects, máquina de estados, `VerificadorDeConflito`, exceções de domínio. Testes unitários puros (sem Spring). Ver `01-dominio.md`.
- **Fase 2 — Casos de uso + adapters em memória**: as 7 portas de entrada, portas de saída, eventos de domínio, adapters em memória (repositórios, gateway de pagamento fake, publicador de eventos, clock real). `ArchitectureTest` (ArchUnit). Smoke test do contexto Spring completo em memória. Ver `02-casos-de-uso.md`.
- **Fase 3 — Persistência real + API REST**: entidades JPA, mappers, migrations Flyway, repository adapters PostgreSQL, testes de integração com Testcontainers (pendente de execução — requer Docker Desktop rodando neste ambiente), troca de adapter em memória ↔ PostgreSQL via `@Profile("dev")`/`@Profile("!dev")`. Controllers REST + DTOs + `GlobalExceptionHandler`, testados com `@WebMvcTest`. Ver `03-api-rest.md`.
- **Fase 4, item 1 — Gateway de pagamento Pix real (Asaas)**: `AsaasGatewayAdapter` (`@Profile("!dev")`) integra de verdade com `api-sandbox.asaas.com/v3` — cria o cliente no Asaas, cria a cobrança Pix (com `agendamentoId` como `externalReference`) e busca o QR Code. `AsaasWebhookController` (`POST /api/webhooks/asaas`) recebe a confirmação real, validando o header `asaas-access-token` contra `asaas.webhook-token`. Testado com WireMock (adapter) e `@WebMvcTest` (webhook), sem chamar a API real. Config em `asaas.*`, chave/token lidos de `ASAAS_API_KEY`/`ASAAS_WEBHOOK_TOKEN` (vazios por padrão — a aplicação sobe normalmente sem eles, só não consegue emitir cobranças reais). A porta `GatewayDePagamento` ganhou o parâmetro `Cliente` (necessário para criar o cliente no Asaas) — mudança que se propagou para `GatewayDePagamentoFake` e `CriarAgendamentoService`. Ver `02-casos-de-uso.md` e `03-api-rest.md`.
- **Fase 4, item 3 — Scheduler de expiração**: `ExpiracaoReservaScheduler` (`adapter/in/scheduler/`) aciona `ExpirarReservasPendentesUseCase` periodicamente via `@Scheduled`, intervalo configurável em `agendamento.expiracao.intervalo-ms` (padrão 60s). Usa `initialDelay` igual ao `fixedDelay` para não disparar no instante em que qualquer teste sobe o contexto Spring completo. Testado isoladamente (chamada direta ao método, sem depender do agendador do Spring). Ver `02-casos-de-uso.md`.
- **Fase 4, item 3 — Notificações multicanal (canal e-mail)**: porta `EnviadorDeNotificacao` + `NotificacaoDispatcher` (roteia por `CanalNotificacao`) + `NotificacaoEventListener` (`adapter/in/evento/`, reage a `AgendamentoCriado`/`AgendamentoConfirmado`/`AgendamentoCancelado` via `@EventListener`, falhas de envio só logadas, nunca propagadas). `PublicadorDeEventosSpring` (`@Profile("!dev")`) passou a delegar ao `ApplicationEventPublisher` do Spring para o listener conseguir reagir de verdade — antes só existia a versão em memória que apenas acumulava eventos sem nenhum consumidor. `AgendamentoConfirmado`/`AgendamentoCancelado` ganharam o campo `clienteId`. Canal real implementado: `EmailEnviadorDeNotificacao` (`@Profile("!dev")`, SMTP via `JavaMailSender`, testado com GreenMail). `SMS` e `WHATSAPP` existem no enum `CanalNotificacao` mas sem adapter real ainda — ver pendências abaixo. Ver `02-casos-de-uso.md`.
- **Fase 4, item 1 — Segundo gateway de pagamento (Mercado Pago)**: `MercadoPagoGatewayAdapter` + `MercadoPagoWebhookController`, ativos só quando `pagamento.gateway=mercadopago` (`@ConditionalOnProperty`, `AsaasGatewayAdapter`/`AsaasWebhookController` viraram o padrão explícito com `matchIfMissing = true`). **Essa é a demonstração real de troca de gateway via configuração** que o projeto persegue desde o plano inicial — nenhuma linha de código de aplicação ou domínio muda, só a propriedade `PAGAMENTO_GATEWAY`. Integração propositalmente diferente da do Asaas, preservando o que cada gateway realmente exige (registrado como comentário na classe): sem "criar cliente" separado (dados do pagador vão direto no corpo), JSON em snake_case, webhook que só traz o id do pagamento (não o status — precisa de uma segunda chamada, `consultarPagamento`), assinatura HMAC-SHA256 no header `x-signature` em vez de token simples. Config em `mercadopago.*`, testado com WireMock (adapter) e `@WebMvcTest` (webhook, incluindo validação de assinatura válida/inválida). Ver `02-casos-de-uso.md` e `03-api-rest.md`.
- **Fase 4, item 3 — Sincronização com Google Calendar**: `CalendarioExternoPort` (`sincronizarEvento`/`removerEvento`) + `CalendarioEventListener` (`adapter/in/evento/`), reagindo só a `AgendamentoConfirmado` (cria o evento) e `AgendamentoCancelado` (remove) — propositalmente não reage a `AgendamentoCriado`, já que um agendamento pendente de pagamento pode expirar sem nunca ocupar a agenda de verdade. `GoogleCalendarAdapter` (`@Profile("!dev")`) autentica via conta de serviço (`com.google.auth:google-auth-library-oauth2-http`, sem fluxo OAuth2 interativo) e chama a API REST do Google Calendar diretamente (mesmo estilo dos gateways de pagamento — sem SDK pesado). O id do evento no Google é derivado deterministicamente do `agendamentoId` (hex do UUID sem hífens), dispensando um mapeamento à parte. Testado com WireMock, inclusive o próprio token server (`google-calendar.token-server-uri`, redirecionável para o WireMock em teste — a lib assina o JWT localmente com uma chave RSA descartável gerada em memória, nunca validada pelo WireMock). Config em `google-calendar.*`, credenciais vazias por padrão (a aplicação sobe normalmente sem elas, só não sincroniza de verdade). Ver `02-casos-de-uso.md`.
- **Demonstração via browser (Swagger UI)**: adicionado `springdoc-openapi-starter-webmvc-ui`, expondo `/swagger-ui.html` para exercitar a API REST interativamente. `DevDataSeeder` (`adapter/in/seed/`, `@Profile("dev")`) popula prestador/cliente/serviço de IDs fixos no startup, só para permitir testar `POST /api/agendamentos` pelo Swagger sem precisar de endpoints de cadastro (fora do escopo deste projeto). Nessa investigação ficou claro que o perfil `dev` só trocava os adapters de negócio — Flyway/DataSource/JPA continuavam ativos e a aplicação real (fora dos testes, que já excluíam essas auto-configurações manualmente) não subia sem Postgres. Corrigido com um documento de perfil dedicado em `application.yml` (`spring.config.activate.on-profile: dev` excluindo `HibernateJpaAutoConfiguration`/`DataSourceAutoConfiguration`/`DataSourceTransactionManagerAutoConfiguration`/`FlywayAutoConfiguration`), removendo a exclusão duplicada que só existia em `AgendamentoApplicationTests`.
- **Fase 4, item 3 — Canais WhatsApp e SMS reais (Twilio)**: `TwilioSmsEnviadorDeNotificacao` e `TwilioWhatsAppEnviadorDeNotificacao` (`@Profile("!dev")`), ambos chamando a mesma Twilio Messages API (`POST /Accounts/{sid}/Messages.json`, form-urlencoded, Basic Auth) via `AbstractTwilioEnviadorDeNotificacao` — a única diferença entre os dois é o prefixo `whatsapp:` no `From`/`To`. Números sem código do país recebem `+55` automaticamente (o domínio não força DDI, mas a API do Twilio exige E.164). Config em `twilio.*` (`TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_SMS_FROM`/`TWILIO_WHATSAPP_FROM`, esse último com o número sandbox público da Twilio como padrão). Testado com WireMock, verificando header de autenticação e corpo do form. `NotificacaoEventListener` continua disparando só `EMAIL` — qual canal usar por evento segue como decisão em aberto (ver pendências). Ver `02-casos-de-uso.md`.
- **Perfil `dev` reclassificado como uso exclusivo de testes**: os adapters em memória (repositórios, `GatewayDePagamentoFake`, `PublicadorDeEventosEmMemoria`, `EnviadorDeNotificacaoFake`, `CalendarioExternoFake`) continuam existindo e sendo usados como dublês nos testes de serviço/aplicação — prática padrão de mercado para isolar regras de negócio de infraestrutura, não um atalho de portfólio. O que mudou é a documentação (`CLAUDE.md`): rodar/demonstrar a aplicação de verdade deve sempre usar o perfil padrão com Postgres real (`docker-compose up -d`), nunca mais o perfil `dev` — confirmado rodando a aplicação contra o Postgres do `docker-compose.yml` (Flyway migrou as 4 tabelas, `GET /api/agendamentos/{id}` respondeu 404 consultando o banco de verdade, com todos os adapters `!dev` — Asaas, Twilio, Google Calendar — construídos com sucesso mesmo sem credenciais configuradas).
- **Fase 4, item 1 — Execução de estorno no cancelamento**: `GatewayDePagamento` ganhou `estornar(referenciaExterna, valor)`, implementado por `AsaasGatewayAdapter` (`POST /payments/{id}/refund`) e `MercadoPagoGatewayAdapter` (`POST /v1/payments/{id}/refunds`, com `X-Idempotency-Key`). `Agendamento` ganhou o campo `referenciaPagamento` (nullable, coluna nova `referencia_pagamento` — migration `V5`) e o método `vincularReferenciaPagamento(String)`, chamado por `CriarAgendamentoService` logo após gerar a cobrança Pix. `EstornoEventListener` (`adapter/in/evento/`) reage a `AgendamentoCancelado` — mesmo padrão de `NotificacaoEventListener`/`CalendarioEventListener`: só age quando há valor a reembolsar (`resultado.valorReembolsado() > 0`) e o agendamento tem uma referência de pagamento vinculada; falhas são logadas e nunca propagadas, já que o cancelamento em si já foi persistido antes desse efeito colateral. Testado com WireMock (adapters) e dublê de porta (listener). Ver `02-casos-de-uso.md`.

- **Fase 4, item 3 — Canal de notificação por evento decidido**: `NotificacaoEventListener` dispara dois canais por evento — `EMAIL` (registro formal) e `WHATSAPP` (canal que o cliente brasileiro de fato confere para esse tipo de aviso), cada um isolado no seu próprio try/catch (`enviarPorCanal`) para a falha de um não impedir o outro. `SMS` fica com adapter pronto e testado, mas não utilizado — dois canais já cobrem o caso de uso sem a redundância de um terceiro aviso repetindo a mesma informação. Ver `02-casos-de-uso.md`.
- **Frontend separado + endpoints de cadastro**: até aqui `Prestador`/`Cliente`/`Servico` não tinham nenhum endpoint REST (só existiam via `DevDataSeeder` ou SQL manual) — impossível "rodar o projeto inteiro" numa tela sem eles. Adicionados `PrestadorController` (`POST`/`GET /api/prestadores`), `ClienteController` (`POST`/`GET /api/clientes`), `ServicoController` (`POST /api/servicos`, `GET /api/servicos?prestadorId=`), cada um com seu caso de uso em `application/port/in` + `application/service`, seguindo exatamente o padrão de `AgendamentoController`/`CriarAgendamentoService`. `PrestadorRepository`/`ClienteRepository` ganharam `buscarTodos()` e `ServicoRepository` ganhou `buscarPorPrestador(PrestadorId)` (ambos implementados nos adapters em memória e JPA — no JPA, `buscarTodos` usa o `findAll()` que `JpaRepository` já dá de graça, `buscarPorPrestador` usa uma query derivada nova, `findByPrestadorId`). Nenhuma migration nova — as tabelas já existiam desde a Fase 3. Adicionado também `WebConfig` (`adapter/in/web/`) com CORS liberado para `app.cors.allowed-origins` (`http://localhost:5173` por padrão) — sem isso o browser bloqueia as chamadas do frontend antes de chegarem à API. Um frontend React + Vite + JavaScript puro + CSS puro foi criado em `frontend/` (projeto Node totalmente separado, comunicação só via REST/CORS) com páginas para cadastrar prestador/serviço/cliente, criar um agendamento, simular o pagamento, cancelar e marcar no-show — o fluxo completo do projeto, de ponta a ponta, numa interface em vez de Swagger/curl. Ver `02-casos-de-uso.md`, `03-api-rest.md` e `CLAUDE.md`.
- **Regra: nenhum id de cadastro ou senha aparece na UI/repositório**: pedido explícito do usuário, documentado em `CLAUDE.md` como regra permanente. `GET /api/clientes` (que inicialmente não existia — a primeira versão do frontend pedia pro usuário colar o UUID do cliente) foi adicionado justamente pra isso: a tela de novo agendamento troca o campo de texto por um `<select>` de clientes por nome. `PrestadoresPage`/`ServicosPage` perderam a coluna "Id" da tabela, `ClientesPage` parou de mostrar o id após cadastrar (mostra uma tabela de clientes já cadastrados em vez disso), e as telas de agendamento pararam de exibir o id como texto (o id continua existindo tecnicamente como `value` de `<option>` e parâmetro de rota na URL — isso não conta como "aparecer na tela"). Nenhuma credencial real é commitada (já era assim para todas as integrações externas); único texto-plano aceito conscientemente é a senha do Postgres local em `docker-compose.yml`/`application.yml` (container descartável, só em `localhost`). Validado também o fluxo completo com sinal usando o perfil `dev` (único jeito de testar a cobrança Pix sem credenciais reais do Asaas): criar agendamento → `PENDENTE_PAGAMENTO` com cobrança fake → simular pagamento → `CONFIRMADO`.
- **`Prestador` ganha `telefone`**: pedido explícito do usuário — a listagem de prestadores deveria mostrar telefone, não CNPJ. `Prestador` não tinha nenhum dado de contato até aqui (só `nome`, `documento`, `politicaCancelamentoPadrao`), então foi um campo novo de verdade, não só uma troca de exibição: construtor de `Prestador` ganhou `telefone` (validado com o mesmo padrão de `Contato.telefone`, mas como campo simples — `Prestador` já valida `nome` do mesmo jeito, sem VO dedicado), migration `V6` (`ALTER TABLE` + backfill de linhas existentes com um placeholder, já que a coluna é `NOT NULL`), `PrestadorJpaEntity`/`PrestadorMapper`/`CadastrarPrestadorCommand`/`CadastrarPrestadorRequest`/`PrestadorResponse` atualizados, e todo call site de `new Prestador(...)` no projeto (11 arquivos) ajustado para o novo parâmetro. A API continua retornando `documentoNumero`/`documentoTipo` normalmente (o dado não sumiu, só a tela de prestadores passou a mostrar `telefone` em vez de documento). Testado de ponta a ponta contra o Postgres real, inclusive confirmando que linhas antigas (sem telefone) foram migradas com o placeholder e que um cadastro novo grava o telefone de verdade.
- **Redesign visual do frontend**: pedido explícito do usuário por um design "mais arrojado, moderno, com cores melhores e botões mais ativos". Paleta roxo/ciano com gradientes, tipografia `Sora`+`Inter` (Google Fonts), botões com hover/active mais expressivos (a regra CSS passou de `.form button, .acoes button` para `button` genérico — cobria um buraco real: o botão "Gerenciar este agendamento" em `NovoAgendamentoPage` ficava sem estilo nenhum antes disso), badge de status colorido por valor (`status-badge`, com `data-status` dirigindo a cor) em vez de texto plano, navbar sticky, tabelas com hover nas linhas. Puro CSS, sem framework novo — mantém a decisão original de "CSS puro" do projeto.
- **Levantamento de gaps para produção**: pedido explícito do usuário ("o que falta pra esse projeto ser funcional e produtivo"). Identificados: ausência de qualquer listagem/agenda (maior gap funcional — sem ela, depois de sair da tela de criação não havia nenhum jeito de reencontrar um agendamento, dado que id nunca aparece na UI), zero autenticação/autorização (`spring-security` nem está no `pom.xml` — qualquer requisição mexe em qualquer prestador), CRUD incompleto de cadastro (só `POST`/`GET`, sem `PUT`/`DELETE`), ausência de `Dockerfile` da aplicação e de pipeline de CI, ausência de `spring-boot-starter-actuator`, zero teste automatizado no frontend, além dos itens já listados abaixo em "Pendente". Priorizado por este levantamento: listagem/agenda primeiro (bloqueia uso de ponta a ponta), autenticação básica em seguida (bloqueia chamar o projeto de "produtivo" com qualquer dado real).
- **Listagem/agenda por prestador**: primeiro item do levantamento acima, implementado nesta sessão. `AgendamentoRepository` ganhou `buscarPorPrestador(PrestadorId)` (distinto de `buscarAtivosPorPrestador`, usado pelo `VerificadorDeConflito` — este novo método retorna qualquer status, inclusive histórico `CANCELADO`/`NO_SHOW`, ordenado por `periodo.inicio` ascendente; implementado em `InMemoryAgendamentoRepository` e via `AgendamentoJpaRepository.findByPrestadorIdOrderByPeriodoInicioAsc`), novo caso de uso `ListarAgendamentosPorPrestadorUseCase`/`Query` (mesmo padrão sem-404-se-vazio de `ListarServicosPorPrestadorUseCase`), novo `GET /api/agendamentos` em `AgendamentoController` (na época, ainda com `prestadorId` como query param — depois da autenticação, abaixo, passou a derivar da sessão). No frontend, nova página `AgendaPage` (rota `/agenda`, página inicial do app): lista os agendamentos numa tabela resolvendo nome de cliente/serviço no cliente (reaproveitando `GET /api/clientes`/`GET /api/servicos?prestadorId=`, já buscados em outras telas), com um botão "Abrir" por linha navegando para `/agendamentos/:id` (id só como parâmetro de rota, nunca como texto renderizado — mesma regra de sempre). Testado via `@WebMvcTest`/teste de serviço com adapter em memória/`*RepositoryAdapterIT` e validado ao vivo contra o Postgres real e no navegador.
- **Autenticação de Prestador (login simples)**: segundo item do levantamento acima, implementado nesta sessão. Escopo deliberadamente restrito, decidido com o usuário: só `Prestador` autentica (sessão via cookie, Spring Security); `Cliente` continua sem login, e o fluxo público de reserva inteiro (listar prestador/serviço, cadastrar cliente, criar/consultar/cancelar/marcar no-show um agendamento, webhooks de pagamento) continua liberado sem autenticação — só a área de gestão do próprio prestador (`GET /api/agendamentos`, agora sem `prestadorId` no query string — vem da sessão; `POST /api/servicos`, agora sem `prestadorId` no corpo) passou a exigir login. `spring-boot-starter-security` adicionado ao `pom.xml`. `Prestador` ganhou `email` (único) e `senhaHash` (BCrypt, nunca exposto); migration `V7` com backfill (placeholder de email único por linha via `id`, hash bcrypt público de exemplo — nenhum segredo real, mesmo espírito do placeholder de `telefone` na `V6`). `CadastrarPrestadorService` passou a injetar `PasswordEncoder` para gerar o hash. Novo pacote `adapter/in/web/security/`: `PrestadorPrincipal`/`PrestadorUserDetailsService` (Spring Security `UserDetails`/`UserDetailsService`), `SecurityConfig` (`SecurityFilterChain`, CORS com `CorsConfigurationSource` próprio — a integração automática via `HandlerMappingIntrospector` do Spring MVC quebra nos testes de persistência, que sobem o contexto sem MVC —, `/error` liberado para não mascarar um 500 de verdade como 401). Novo `AuthController` (`POST /api/auth/login`/`logout`, `GET /api/auth/me`) com login "na mão" via `AuthenticationManager` + `HttpSessionSecurityContextRepository`, em vez do `formLogin()` padrão do Spring Security (pensado para formulário HTML, não para uma API JSON consumida por um frontend separado). **Todo `@WebMvcTest` do projeto precisou de `@Import(SecurityConfig.class)`** — mesma causa raiz do incidente do `CorsProperties` registrado antes nesta mesma lista (um `@Configuration` plano não é um dos estereótipos que a fatia de teste inclui sozinha; sem o import, a fatia caía no `SecurityFilterChain` padrão auto-configurado do Spring Boot, com CSRF habilitado e tudo exigindo login, mascarando os testes existentes com 401/403 em massa). No frontend: `src/auth/AuthContext.jsx` (estado de login, verificado uma vez via `GET /api/auth/me`) + `src/auth/RequireAuth.jsx` (protege `/agenda` e `/servicos`, redireciona para `/login`), nova `LoginPage`, `NavBar` mostra "Entrar" ou nome+"Sair", `PrestadoresPage` ganhou campos de email/senha no cadastro (é o sign-up), `ServicosPage` parou de deixar escolher "qualquer prestador" — gerencia só os serviços do prestador logado. `api/client.js` manda `credentials: 'include'` em toda chamada (cookie de sessão entre origens diferentes) — exige `allowCredentials(true)` no CORS do backend. Validado de ponta a ponta via curl (cadastro → login → cadastro de serviço autenticado → listar agenda autenticado → tentativa sem login rejeitada com 401 → logout → sessão invalidada) e compilação limpa do frontend.
- **Auditoria de qualidade de código (01/10/2026)**: pedido explícito do usuário — relatório formal (resumo, entregue, pendente, achados de qualidade com arquivo:linha, plano de ação priorizado P0/P1/P2) publicado como Artifact e depois salvo localmente pelo usuário. Achados confirmados: `TELEFONE_PATTERN`/`EMAIL_PATTERN` duplicados entre `Contato` e `Prestador`; CORS duplicado entre `WebConfig` e `SecurityConfig`; helper de teste `autenticacaoDoPrestador(...)` copiado entre `AgendamentoControllerTest`/`ServicoControllerTest`; `POST /api/auth/logout` sem `permitAll` (401 em vez do 204 documentado se chamado deslogado — comportamento correto, só faltava no spec); `DataIntegrityViolationException` não tratada (virava 500 cru). **Nenhum bug de lógica/corretude encontrado** — a regra de sinal obrigatório por no-show, as regras de `authorizeHttpRequests`, o `logout`, e a busca de prestador por email foram verificados e batem com o domínio/spec. Todos os achados acionáveis foram corrigidos nesta mesma sessão (ver entradas abaixo); o plano de ação completo virou as pendências/entregas desta lista.
- **CSRF reativado + CORS consolidado**: execução do plano de ação da auditoria acima (P0 + P1). `SecurityConfig` passou a usar `CookieCsrfTokenRepository.withHttpOnlyFalse()` + `CsrfTokenRequestAttributeHandler`, excluindo só `/api/webhooks/**` (Asaas/Mercado Pago chamam sem cookie de sessão; autenticidade já garantida por token/assinatura nos próprios controllers). Novo `CsrfCookieFilter` força o cookie `XSRF-TOKEN` a ser gravado em toda requisição (inclusive `GET`) — sem ele o Spring Security só grava na primeira vez que algo lê o token, o que nunca aconteceria sozinho numa API sem views server-side. `frontend/src/api/client.js` lê o cookie e reenvia como header `X-XSRF-TOKEN` em toda chamada que não seja `GET`. `WebConfig` foi **removido**: sua config de CORS duplicava a de `SecurityConfig` (achado da auditoria) e nunca era, de fato, quem decidia CORS em produção (o Security governa toda a cadeia de qualquer forma) — `@EnableConfigurationProperties(CorsProperties.class)` migrou para `SecurityConfig`. Todo `@WebMvcTest` que faz `POST`/`PUT`/`DELETE` ganhou `.with(csrf())` nas chamadas de teste.
- **`DataIntegrityViolationException` tratada**: `GlobalExceptionHandler` ganhou um `@ExceptionHandler` pra essa exceção (409, mensagem genérica) — documento ou email duplicado, ou exclusão com vínculo de chave estrangeira, agora dão uma resposta limpa em vez de um 500 cru.
- **Débito técnico dos testes de persistência corrigido**: os 3 bugs documentados abaixo (isolamento, `Instant`, `BigDecimal`) foram corrigidos. `AbstractPersistenceIT` ganhou `@Transactional` (rollback automático por método, resolve o problema de isolamento pra `AgendamentoRepositoryAdapterIT`/`ClienteRepositoryAdapterIT`/`ServicoRepositoryAdapterIT`/`PrestadorRepositoryAdapterIT` de uma vez). A comparação de `Instant` em `AgendamentoRepositoryAdapterIT` virou `isCloseTo(..., within(1, ChronoUnit.MILLIS))` — tentar truncar pra microssegundo (a correção sugerida originalmente) não funcionou porque o round-trip via driver JDBC introduz um resíduo sub-microssegundo às vezes, não um truncamento exato; `isCloseTo` é mais robusto porque não depende de saber exatamente que precisão o driver preserva. A comparação de `PoliticaCancelamento` em `PrestadorRepositoryAdapterIT` passou a comparar `antecedenciaMinima`/`percentualRetido` campo a campo (`isEqualByComparingTo` pro `BigDecimal`) em vez do record inteiro. **Os 4 testes passam individualmente** — rodar os 4 juntos no mesmo fork local às vezes falha com `CannotCreateTransaction`/conexão recusada por limitação de recursos desta máquina (múltiplos contextos Spring + Testcontainers em sequência), não por bug; o CI (`.github/workflows/ci.yml`, runner do GitHub Actions) roda a suíte inteira de uma vez sem esse problema.
- **CRUD completo para Prestador/Cliente/Servico**: `PUT`/`DELETE /api/clientes/{id}` (público), `PUT`/`DELETE /api/servicos/{id}` (autenticado, com checagem de dono — `AcessoNaoAutorizadoException` nova, mapeada pra 403, se o serviço não pertence ao prestador autenticado), `PUT /api/prestadores/{id}` (autenticado, só o próprio perfil — nome/telefone; documento/email/senha imutáveis por essa via). `Prestador.atualizarPerfil(...)`, `Cliente.atualizarDadosCadastrais(...)`, `Servico.atualizarDados(...)` são os novos métodos de domínio (entidades já eram mutáveis, ver `01-dominio.md`). Não existe `DELETE /api/prestadores/{id}` — excluir a própria conta logada envolveria invalidar a sessão e decidir o que fazer com serviços/agendamentos vinculados, adiado conscientemente. `ClienteRepository`/`ServicoRepository` ganharam `excluir(id)`.
- **Dockerfile + CI + Actuator**: `Dockerfile` multi-estágio (build com Maven, imagem final só com o jar numa JRE Alpine) + `.dockerignore`; `docker-compose.yml` ganhou o serviço `app` (healthcheck no Postgres antes de subir, variáveis `SPRING_DATASOURCE_*` via binding relaxado do Spring Boot — mesmo `application.yml`, só troca `localhost` por `postgres`). `.github/workflows/ci.yml` roda a suíte inteira (inclusive `ArchitectureTest` e os `*RepositoryAdapterIT` — o runner do GitHub Actions já tem Docker, sem a limitação de recursos desta máquina local) + build da imagem Docker, e builda o frontend separadamente. `spring-boot-starter-actuator` com só `/health` exposto (`management.endpoints.web.exposure.include: health`, `show-details: never`); indicador de saúde do `spring-mail` desabilitado (`management.health.mail.enabled: false`) — achado testando o container: `spring-boot-starter-mail` registra um health check que tenta conectar no SMTP configurado, e isso derrubava o `/health` inteiro mesmo com a aplicação e o banco saudáveis, já que SMTP é integração opcional aqui.
- **Duplicação de código eliminada**: `TELEFONE_PATTERN`/`EMAIL_PATTERN` extraídos para `domain/model/shared/FormatoContato`, reaproveitado por `Contato` e `Prestador` (achado da auditoria). Helper de teste `autenticacaoDoPrestador(...)` extraído para `TestAutenticacao` (`adapter/in/web/security/`, fonte de teste), reaproveitado por `AgendamentoControllerTest`, `ServicoControllerTest` e `PrestadorControllerTest`.

## Pendente — Fase 4 (demais integrações, uma por vez)

1. **Retry/observabilidade de estornos que falham** — hoje uma falha no `EstornoEventListener` só é logada; não há fila de reprocessamento nem alerta. Aceitável para portfólio, mas um gap real de produção (dinheiro que deveria ter sido devolvido e não foi, sem nenhum rastro além do log).
2. **Canal preferido por cliente** — hoje todo cliente recebe email + WhatsApp para todo evento; um campo de preferência em `Contato` permitiria personalizar, mas exigiria migração de schema e não foi pedido ainda.
3. **Vulnerabilidades moderadas no `frontend/` (`npm audit`)** — `esbuild`/`vite` (exposição do dev server, só relevante se outra máquina na rede alcançar `localhost:5173` enquanto o servidor estiver de pé) e `react-router` (bypass de redirect e injeção via hidratação SSR — este projeto é só client-side, sem SSR, então o segundo não se aplica de verdade aqui). Corrigir exigiria `vite@8`/`react-router-dom@7` (major bumps) — não aplicado ainda para não arriscar quebrar algo sem necessidade imediata.
4. **Modelagem Estabelecimento vs. Profissional** — discutido em sessão: o domínio atual funde os dois em `Prestador` (um prestador = uma agenda só). Separar em duas entidades (`Estabelecimento` dono de vários `Profissional`, cada um com disponibilidade própria) e adicionar um conceito de "horário bloqueado" (ocupação de agenda sem agendamento de cliente por trás) é uma extensão de domínio real, não um ajuste cosmético — ainda não decidido se vale a pena para este projeto.
5. **Zero teste automatizado no frontend** — `frontend/package.json` só tem `dev`/`build`/`preview`; sem `vitest`, `@testing-library/react` ou `eslint` configurado.
6. **Só `Prestador` autentica (risco aceito conscientemente)** — decisão de escopo explícita, reavaliada e mantida na auditoria de 01/10/2026: `Cliente` continua sem login, então qualquer um que descubra um `agendamentoId` consegue consultar/cancelar/marcar no-show esse agendamento (o id nunca aparece como texto na UI, mas nada impede alguém de interceptar/compartilhar a URL). Resolver de verdade exigiria login de `Cliente` também — dobra o escopo de autenticação (duas telas de login, dois modelos de permissão). Ver `specs/02-casos-de-uso.md`.

## Débito técnico conhecido

Nenhum no momento. Os 3 bugs anteriores dos testes `*RepositoryAdapterIT` (isolamento entre métodos, comparação de `Instant`, comparação de `BigDecimal`) foram corrigidos nesta sessão — ver "Entregue" acima. A única ressalva que resta não é débito técnico, é limitação de recursos desta máquina local: rodar os 4 testes `*RepositoryAdapterIT` juntos no mesmo fork Maven às vezes falha com `CannotCreateTransaction`/conexão recusada (múltiplos contextos Spring + Testcontainers em sequência disputando memória); rodar cada classe sozinha, ou deixar o CI (com mais recursos) rodar a suíte inteira, não tem esse problema.
