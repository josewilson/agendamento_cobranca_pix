## Projeto

Agendamento com cobrança via Pix — uma plataforma de agendamento para prestadores de serviço (clínicas, barbearias, estúdios) com cobrança de sinal/multa de cancelamento via Pix. Projeto de portfólio em arquitetura hexagonal, Java 21 + Spring Boot 3.5.11.

## Comandos

Não há `mvn` nem Maven wrapper (`mvnw`) no PATH deste ambiente, e `.mvn/` não tem o jar do wrapper. Use as ferramentas MCP do IntelliJ:

- Build/compilar: `mcp__idea__build_project`. Passe `rebuild: true` se um build incremental reportar sucesso mas um teste ainda falhar numa classe desatualizada — isso já aconteceu depois de editar um arquivo do qual muitos outros dependem (ex.: adicionar `@Profile` em vários adapters de uma vez).
- Rodar uma classe ou método de teste isolado: `mcp__idea__get_run_configurations` com `filePath` para obter a linha da classe/método, depois `mcp__idea__execute_run_configuration` com esse `filePath` + `line`.
- Se um `mvn`/`mvnw` real estiver disponível, os equivalentes são `mvn compile`, `mvn test`, `mvn -Dtest=NomeDaClasse#metodo test`, `mvn spring-boot:run`.

### Rodando a aplicação / testes de integração localmente

- `docker-compose up -d` sobe a instância do Postgres que o perfil Spring padrão precisa (configuração do datasource em `src/main/resources/application.yml`; o schema vem das migrations Flyway em `src/main/resources/db/migration`, validadas contra as entidades JPA na subida via `spring.jpa.hibernate.ddl-auto=validate`).
- As classes `*RepositoryAdapterIT` em `adapter/out/persistence/jpa` usam Testcontainers (um container Postgres descartável, independente do docker-compose) — o Docker Desktop precisa estar rodando ou elas falham ao subir o container.
- O perfil Spring `dev` troca todos os adapters de persistência e o de pagamento pelos em memória/fake (ver Arquitetura abaixo) — sem precisar de Postgres nem de credenciais do Asaas. `AgendamentoApplicationTests` (o smoke test de contexto) roda sob `@ActiveProfiles("dev")` por esse motivo.
- Integração real com o Asaas exige `ASAAS_API_KEY` e `ASAAS_WEBHOOK_TOKEN` (variáveis de ambiente); sem elas a aplicação sobe normalmente (perfil padrão), só não consegue emitir cobranças reais.

## Arquitetura

Hexagonal (portas e adapters), garantida por `src/test/java/.../architecture/ArchitectureTest.java` (ArchUnit): domínio não pode depender de Spring, JPA, nem de `adapter.*`; aplicação não pode depender de `adapter.*` nem de JPA; sem ciclos de pacotes entre `domain`/`application`/`adapter`.

- **`domain/`** — Java puro, zero imports de framework. `model/` tem as entidades (`Agendamento`, `Cliente`, `Prestador`, `Servico` — mutáveis, igualdade por identidade) e os value objects (`Periodo`, `Dinheiro`, `Contato`, `DocumentoFiscal`, `PoliticaCancelamento` — `record`s com construtores compactos que validam). O switch `transicoesValidas()` de `StatusAgendamento` é a única fonte de verdade da máquina de estados do agendamento. `service/VerificadorDeConflito` é o único domain service (checagem de conflito de horário). `event/` tem uma `sealed interface EventoDeDominio` e suas implementações em `record`.
  - `Agendamento.criar(...)` é o único jeito de criar um agendamento *novo* — valida "não no passado" e deriva o status inicial de se há sinal devido. `Agendamento.reconstituir(...)` é o caminho separado que os adapters de persistência usam para reidratar uma linha do banco sem reaplicar essa validação de criação (um agendamento histórico, já concluído, precisa carregar mesmo com o período no passado).
  - Valor monetário é sempre `Dinheiro` (envolve `BigDecimal`, escala normalizada para 2 via `HALF_EVEN` no construtor compacto) — nunca `double`/`float`.
- **`application/`** — orquestração dos casos de uso. `port/in` tem uma interface + um `record` de Command/Query por caso de uso (criar, confirmar, cancelar, marcar no-show, expirar reservas pendentes, processar webhook de pagamento, consultar por id). `port/out` tem uma interface de repositório por agregado, mais `GatewayDePagamento`, `PublicadorDeEventos` e `Clock` (abstrai `Instant.now()` para as regras sensíveis a tempo serem testáveis deterministicamente). `service/*Service` implementam as portas `in` como beans `@Service` — aplicação *pode* depender de Spring, só `domain` é livre de framework. `ProcessarWebhookPagamentoService` só delega para `ConfirmarAgendamentoUseCase`; propositalmente não há outro jeito de confirmar um agendamento (nenhum endpoint REST manual de "confirmar").
- **`adapter/in/web/`** — controllers REST + um DTO por request/response + `GlobalExceptionHandler` mapeando exceções de domínio/aplicação para status HTTP (404 `RecursoNaoEncontradoException`, 409 `ConflitoDeHorarioException`/`TransicaoDeStatusInvalidaException`, 400 falhas de bean validation e `IllegalArgumentException`/`IllegalStateException`). `AsaasWebhookController` (`POST /api/webhooks/asaas`) traduz o payload real do Asaas para `WebhookPagamentoCommand`, validando o header `asaas-access-token` antes de processar qualquer evento.
- **`adapter/in/scheduler/`** — `ExpiracaoReservaScheduler`, um `@Scheduled` que aciona `ExpirarReservasPendentesUseCase` periodicamente (intervalo em `agendamento.expiracao.intervalo-ms`, padrão 60s). Usa `initialDelay` igual ao `fixedDelay` de propósito — sem isso, `@Scheduled` dispara a primeira execução no instante em que o contexto Spring sobe, o que rodaria em todo teste que carrega o contexto completo.
- **`adapter/in/evento/NotificacaoEventListener`** — `@EventListener` para `AgendamentoCriado`/`AgendamentoConfirmado`/`AgendamentoCancelado`; busca o `Cliente` pelo `clienteId` do evento e dispara uma notificação via `NotificacaoDispatcher` (application/service — roteia por `CanalNotificacao` para o `EnviadorDeNotificacao` certo). Falhas de envio são capturadas e logadas ali mesmo, nunca propagadas — um e-mail que falha não pode derrubar o caso de uso que já persistiu o agendamento. Só funciona porque `PublicadorDeEventosSpring` (`@Profile("!dev")`) delega ao `ApplicationEventPublisher` do Spring — os eventos de domínio continuam sendo `record`s puros, só esse adapter conhece Spring.
- **`adapter/out/persistence/jpa/`** — adapters reais para Postgres. As classes de `entity/` são POJOs JPA `@Entity` planos (sem tipos de domínio, sem embeddables) com construtor sem argumentos **público** — precisa ser público porque `mapper/` está num pacote irmão, não no mesmo, então `protected` não seria alcançável de lá. As classes de `mapper/` fazem toda a tradução domínio↔JPA, inclusive reconstruindo os value objects (o que reexecuta a validação deles a cada carregamento). `repository/` são interfaces `JpaRepository` simples; as classes `*RepositoryAdapter` as envolvem e implementam as interfaces de `application/port/out`.
- **`adapter/out/pagamento/asaas/AsaasGatewayAdapter`** (`@Profile("!dev")`) — integra de verdade com a API do Asaas (`api-sandbox.asaas.com/v3`): cria o cliente, cria a cobrança Pix (com o `agendamentoId` como `externalReference`, para o webhook correlacionar sem mapeamento à parte) e busca o QR Code. Usa `RestClient` forçado a HTTP/1.1 — o `HttpClient` da JDK tenta negociar HTTP/2 por padrão, o que quebra contra servidores de teste como o WireMock. Config em `config/AsaasProperties` (`@ConfigurationProperties(prefix = "asaas")`).
- **`adapter/out/notificacao/email/EmailEnviadorDeNotificacao`** (`@Profile("!dev")`) — envia via SMTP com `JavaMailSender` (`spring-boot-starter-mail`), config em `spring.mail.*`/`notificacao.email.remetente`. `SMS` e `WHATSAPP` existem em `CanalNotificacao` mas ainda sem adapter real (ver `specs/04-roadmap.md`).
- **`adapter/out/persistence/memory/`**, `adapter/out/pagamento/memory/GatewayDePagamentoFake`, `adapter/out/evento/PublicadorDeEventosEmMemoria`, `adapter/out/notificacao/memory/EnviadorDeNotificacaoFake`, `adapter/out/clock/SystemClockAdapter` — adapters em memória/fake. Cada um mais seu par `!dev` real implementa as *mesmas* interfaces de `application/port/out` e são mutuamente exclusivos via perfis Spring: `@Profile("dev")` nos de memória/fake, `@Profile("!dev")` nos reais (JPA, `AsaasGatewayAdapter`, `PublicadorDeEventosSpring`, `EmailEnviadorDeNotificacao`) — trocar a tecnologia é só mudança de configuração, nunca de código. Testes de serviço de aplicação também usam os adapters em memória diretamente como dublês de teste (`new InMemoryXxxRepository()`), não mocks, já que são o adapter de verdade, não código exclusivo de teste. `SystemClockAdapter` ainda não tem implementação concorrente (não há por que ter outra), por isso não carrega restrição de `@Profile`.

## Estratégia de testes

- Testes de domínio: JUnit 5 + AssertJ puro, sem contexto Spring. `AgendamentoTestDataBuilder` constrói o agregado com mais parâmetros de construtor.
- Testes de serviço de aplicação: os adapters em memória de verdade (ver acima) mais um dublê de teste escrito à mão, `ClockFixo` (package-private, vive em `application/service/` nas fontes de teste), para controle determinístico de tempo.
- Testes web: `@WebMvcTest` por controller, casos de uso mockados com `@MockitoBean` (não o `@MockBean`, que está deprecated).
- Testes de persistência: as classes `*RepositoryAdapterIT` estendem `AbstractPersistenceIT` (`@Testcontainers` + um `PostgreSQLContainer` compartilhado + `@DynamicPropertySource` conectando o datasource) — ver a exigência de Docker em Comandos acima.
- Teste do gateway de pagamento: `AsaasGatewayAdapterTest` usa WireMock (dependência `wiremock-standalone`, que embute o Jetty necessário — a variante não-standalone `org.wiremock:wiremock` falha ao subir sem ele) para simular a API do Asaas, sem nenhuma chamada real.
- Teste do scheduler: chamada direta ao método do `ExpiracaoReservaScheduler` com o caso de uso mockado, sem depender da infraestrutura de agendamento do Spring.
- Teste do envio de e-mail: `EmailEnviadorDeNotificacaoTest` usa GreenMail (`greenmail-junit5`, servidor SMTP em memória) para verificar o e-mail recebido de verdade, sem mock do `JavaMailSender`.
- `pom.xml` registra o agente byte-buddy do Mockito via goal `properties` do `maven-dependency-plugin` mais `-javaagent` no `argLine` do surefire, seguindo a recomendação do próprio Mockito, para evitar o aviso de depreciação de carregamento dinâmico de agente da JDK.
