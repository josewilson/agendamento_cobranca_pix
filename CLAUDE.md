Leia `specs/` (`00-visao-geral.md` até `04-roadmap.md`) no início de toda sessão neste repositório, junto com este arquivo — eles são a fonte da verdade dos requisitos funcionais, das regras de domínio, do contrato REST e do que já foi entregue vs. o que está pendente. ## Projeto

Agendamento com cobrança via Pix — uma plataforma de agendamento para prestadores de serviço (clínicas, barbearias, estúdios) com cobrança de sinal/multa de cancelamento via Pix. Projeto de portfólio em arquitetura hexagonal, Java 21 + Spring Boot 3.5.11.

## Comandos

Não há `mvn` nem Maven wrapper (`mvnw`) no PATH deste ambiente, e `.mvn/` não tem o jar do wrapper. Use as ferramentas MCP do IntelliJ:

- Build/compilar: `mcp__idea__build_project`. Passe `rebuild: true` se um build incremental reportar sucesso mas um teste ainda falhar numa classe desatualizada — isso já aconteceu depois de editar um arquivo do qual muitos outros dependem (ex.: adicionar `@Profile` em vários adapters de uma vez).
- Rodar uma classe ou método de teste isolado: `mcp__idea__get_run_configurations` com `filePath` para obter a linha da classe/método, depois `mcp__idea__execute_run_configuration` com esse `filePath` + `line`.
- Se um `mvn`/`mvnw` real estiver disponível, os equivalentes são `mvn compile`, `mvn test`, `mvn -Dtest=NomeDaClasse#metodo test`, `mvn spring-boot:run`.

### Rodando a aplicação / testes de integração localmente

- `docker-compose up -d` sobe a instância do Postgres que o perfil Spring padrão precisa (configuração do datasource em `src/main/resources/application.yml`; o schema vem das migrations Flyway em `src/main/resources/db/migration`, validadas contra as entidades JPA na subida via `spring.jpa.hibernate.ddl-auto=validate`).
- As classes `*RepositoryAdapterIT` em `adapter/out/persistence/jpa` usam Testcontainers (um container Postgres descartável, independente do docker-compose) — o Docker Desktop precisa estar rodando ou elas falham ao subir o container. **Atenção**: os 4 testes têm bugs conhecidos de falta de isolamento entre métodos e comparação ingênua de `Instant`/`BigDecimal` — ver "Débito técnico conhecido" em `specs/04-roadmap.md` antes de confiar no resultado deles.
- **O perfil Spring `dev` é de uso exclusivo dos testes** (troca todos os adapters de persistência/pagamento/notificação/calendário pelos em memória/fake — ver Arquitetura abaixo). **Nunca use `dev` para rodar ou demonstrar a aplicação de verdade** — isso sempre deve ser feito com `docker-compose up -d` + perfil padrão (Postgres real), confirmado funcionando (Flyway migra as 4 tabelas, todos os adapters `!dev` sobem mesmo sem credenciais configuradas). Um documento de perfil dedicado em `application.yml` (`spring.config.activate.on-profile: dev`) exclui `HibernateJpaAutoConfiguration`/`DataSourceAutoConfiguration`/`DataSourceTransactionManagerAutoConfiguration`/`FlywayAutoConfiguration` só para esse perfil de teste — sem isso a aplicação ainda tentaria abrir uma conexão JDBC no startup mesmo sem nenhum repositório JPA em uso.
- `DevDataSeeder` (`adapter/in/seed/`, `@Profile("dev")`) popula um prestador/cliente/serviço de IDs fixos (`00000000-...-0001/0002/0003`) no startup — um atalho rápido pro perfil de teste. Fora dele, use os endpoints de cadastro reais: `POST /api/prestadores`, `POST /api/clientes`, `POST /api/servicos` (ver `specs/03-api-rest.md`).
- Integração real com o Asaas exige `ASAAS_API_KEY` e `ASAAS_WEBHOOK_TOKEN`, com o Mercado Pago exige `MERCADOPAGO_ACCESS_TOKEN` e `MERCADOPAGO_WEBHOOK_SECRET`, com o Google Calendar exige `GOOGLE_CALENDAR_CREDENTIALS` (JSON da conta de serviço) e `GOOGLE_CALENDAR_ID`, com o Twilio (SMS/WhatsApp) exige `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_SMS_FROM` (variáveis de ambiente); sem elas a aplicação sobe normalmente (perfil padrão), só não consegue emitir cobranças/sincronizar agenda/enviar SMS-WhatsApp de verdade. Qual gateway de pagamento está ativo é `PAGAMENTO_GATEWAY` (`asaas`, o padrão, ou `mercadopago`) — ver Arquitetura abaixo.

### Frontend (`frontend/`)

Projeto React + Vite + JavaScript puro + CSS puro, **completamente separado do backend** (próprio `package.json`, próprio dev server, zero código compartilhado) — conversa só via REST/CORS. Dá pra executar o fluxo inteiro do projeto numa tela: cadastrar prestador, serviço e cliente, criar um agendamento, simular o pagamento (webhook genérico), cancelar, marcar no-show.

- Rodar: `cd frontend && npm install && npm run dev` — sobe em `http://localhost:5173`. Precisa do backend rodando em `http://localhost:8080` (`docker-compose up -d` + `AgendamentoApplication`, perfil padrão) com CORS liberado para essa origem (já é o padrão em `application.yml`, `app.cors.allowed-origins`).
- `src/api/client.js` é o único ponto que fala com a API (`fetch` nativo, sem axios) — lê a URL base de `VITE_API_BASE_URL` (`.env`, padrão `http://localhost:8080`) e já traduz `ErrorResponse.mensagem` do backend em exceções JS.
- Sem endpoint de listagem para clientes — o id retornado ao cadastrar é a única referência; a tela de novo agendamento pede esse id colado manualmente.
- `npm audit` acusa vulnerabilidades moderadas em `esbuild`/`vite` (exposição do dev server) e `react-router` (bypass de redirect; o aviso de hidratação SSR não se aplica — este projeto não usa SSR). Corrigir exige major bumps (`vite@8`, `react-router-dom@7`) — ver `specs/04-roadmap.md`.

## Arquitetura

Hexagonal (portas e adapters), garantida por `src/test/java/.../architecture/ArchitectureTest.java` (ArchUnit): domínio não pode depender de Spring, JPA, nem de `adapter.*`; aplicação não pode depender de `adapter.*` nem de JPA; sem ciclos de pacotes entre `domain`/`application`/`adapter`.

- **`domain/`** — Java puro, zero imports de framework. `model/` tem as entidades (`Agendamento`, `Cliente`, `Prestador`, `Servico` — mutáveis, igualdade por identidade) e os value objects (`Periodo`, `Dinheiro`, `Contato`, `DocumentoFiscal`, `PoliticaCancelamento` — `record`s com construtores compactos que validam). O switch `transicoesValidas()` de `StatusAgendamento` é a única fonte de verdade da máquina de estados do agendamento. `service/VerificadorDeConflito` é o único domain service (checagem de conflito de horário). `event/` tem uma `sealed interface EventoDeDominio` e suas implementações em `record`.
  - `Agendamento.criar(...)` é o único jeito de criar um agendamento *novo* — valida "não no passado" e deriva o status inicial de se há sinal devido. `Agendamento.reconstituir(...)` é o caminho separado que os adapters de persistência usam para reidratar uma linha do banco sem reaplicar essa validação de criação (um agendamento histórico, já concluído, precisa carregar mesmo com o período no passado).
  - `referenciaPagamento` (nullable, `Optional<String>` no getter) guarda o id da cobrança no gateway de pagamento, vinculado uma única vez via `vincularReferenciaPagamento(String)` — necessário para o `EstornoEventListener` saber o que estornar no cancelamento. `null`/vazio para agendamentos que nunca exigiram sinal.
  - Valor monetário é sempre `Dinheiro` (envolve `BigDecimal`, escala normalizada para 2 via `HALF_EVEN` no construtor compacto) — nunca `double`/`float`.
- **`application/`** — orquestração dos casos de uso. `port/in` tem uma interface + um `record` de Command/Query por caso de uso (criar, confirmar, cancelar, marcar no-show, expirar reservas pendentes, processar webhook de pagamento, consultar por id). `port/out` tem uma interface de repositório por agregado, mais `GatewayDePagamento`, `PublicadorDeEventos` e `Clock` (abstrai `Instant.now()` para as regras sensíveis a tempo serem testáveis deterministicamente). `service/*Service` implementam as portas `in` como beans `@Service` — aplicação *pode* depender de Spring, só `domain` é livre de framework. `ProcessarWebhookPagamentoService` só delega para `ConfirmarAgendamentoUseCase`; propositalmente não há outro jeito de confirmar um agendamento (nenhum endpoint REST manual de "confirmar").
- **`adapter/in/web/`** — controllers REST + um DTO por request/response + `GlobalExceptionHandler` mapeando exceções de domínio/aplicação para status HTTP (404 `RecursoNaoEncontradoException`, 409 `ConflitoDeHorarioException`/`TransicaoDeStatusInvalidaException`, 400 falhas de bean validation e `IllegalArgumentException`/`IllegalStateException`). `AsaasWebhookController` (`POST /api/webhooks/asaas`) traduz o payload real do Asaas para `WebhookPagamentoCommand`, validando o header `asaas-access-token` antes de processar qualquer evento. `MercadoPagoWebhookController` (`POST /api/webhooks/mercadopago`) faz o mesmo para o Mercado Pago, mas o payload de lá só traz o id do pagamento (não o status) — o controller consulta de volta via `MercadoPagoGatewayAdapter.consultarPagamento(id)` e valida a assinatura HMAC-SHA256 no header `x-signature` em vez de um token simples. Os dois webhooks (e os dois gateways de pagamento — ver abaixo) só ficam ativos conforme a propriedade `pagamento.gateway` (`@ConditionalOnProperty`); nenhum código muda para trocar de gateway, só essa propriedade.
  - `PrestadorController` (`POST`/`GET /api/prestadores`), `ClienteController` (`POST /api/clientes`) e `ServicoController` (`POST /api/servicos`, `GET /api/servicos?prestadorId=`) seguem exatamente o mesmo estilo de `AgendamentoController` — cada um com seu caso de uso em `application/port/in`+`application/service` (`CadastrarPrestadorUseCase`, `ListarPrestadoresUseCase`, etc.), DTOs com `static de(...)` para mapear domínio→resposta. `PrestadorRepository.buscarTodos()` e `ServicoRepository.buscarPorPrestador(PrestadorId)` são extensões novas dos ports (implementadas tanto em memória quanto via JPA — no JPA, `buscarPorPrestador` usa a query derivada `ServicoJpaRepository.findByPrestadorId`).
  - `WebConfig implements WebMvcConfigurer` libera CORS (`app.cors.allowed-origins`, `config/CorsProperties`) para o frontend separado (`frontend/`, outra porta). Como `@WebMvcTest` inclui todo `WebMvcConfigurer` do classpath mas não faz component scan geral, `WebConfig` usa `@EnableConfigurationProperties(CorsProperties.class)` na própria classe — sem isso, todo `@WebMvcTest` do projeto (não só os novos) quebraria por não achar o bean `CorsProperties`.
- **`adapter/in/scheduler/`** — `ExpiracaoReservaScheduler`, um `@Scheduled` que aciona `ExpirarReservasPendentesUseCase` periodicamente (intervalo em `agendamento.expiracao.intervalo-ms`, padrão 60s). Usa `initialDelay` igual ao `fixedDelay` de propósito — sem isso, `@Scheduled` dispara a primeira execução no instante em que o contexto Spring sobe, o que rodaria em todo teste que carrega o contexto completo.
- **`adapter/in/evento/NotificacaoEventListener`** — `@EventListener` para `AgendamentoCriado`/`AgendamentoConfirmado`/`AgendamentoCancelado`; busca o `Cliente` pelo `clienteId` do evento e dispara **dois canais** via `NotificacaoDispatcher` (application/service — roteia por `CanalNotificacao` para o `EnviadorDeNotificacao` certo): `EMAIL` (registro formal) e `WHATSAPP` (canal que o cliente brasileiro de fato confere para esse tipo de aviso). Cada canal é enviado num try/catch isolado (`enviarPorCanal`) — a falha de um (ex.: Twilio fora do ar) não impede o outro nem propaga para o caso de uso que já persistiu o agendamento. `SMS` tem adapter pronto mas não é usado (dois canais já bastam, ver `specs/04-roadmap.md`). Só funciona porque `PublicadorDeEventosSpring` (`@Profile("!dev")`) delega ao `ApplicationEventPublisher` do Spring — os eventos de domínio continuam sendo `record`s puros, só esse adapter conhece Spring.
- **`adapter/in/evento/CalendarioEventListener`** — mesmo padrão do `NotificacaoEventListener`, mas só reage a `AgendamentoConfirmado` (cria o evento externo) e `AgendamentoCancelado` (remove); propositalmente ignora `AgendamentoCriado`, já que um agendamento `PENDENTE_PAGAMENTO` pode expirar sem nunca ocupar a agenda de verdade. Delega para `CalendarioExternoPort`.
- **`adapter/in/evento/EstornoEventListener`** — mesmo padrão de novo: reage a `AgendamentoCancelado`, só age quando `resultado.valorReembolsado() > 0`, busca o `Agendamento` para pegar `referenciaPagamento()` (vazio quando o agendamento nunca teve sinal) e chama `GatewayDePagamento.estornar(referencia, valor)`. Falha logada, nunca propagada.
- **`adapter/out/persistence/jpa/`** — adapters reais para Postgres. As classes de `entity/` são POJOs JPA `@Entity` planos (sem tipos de domínio, sem embeddables) com construtor sem argumentos **público** — precisa ser público porque `mapper/` está num pacote irmão, não no mesmo, então `protected` não seria alcançável de lá. As classes de `mapper/` fazem toda a tradução domínio↔JPA, inclusive reconstruindo os value objects (o que reexecuta a validação deles a cada carregamento). `repository/` são interfaces `JpaRepository` simples; as classes `*RepositoryAdapter` as envolvem e implementam as interfaces de `application/port/out`.
- **`adapter/out/pagamento/asaas/AsaasGatewayAdapter`** (`@Profile("!dev")` + `@ConditionalOnProperty(pagamento.gateway=asaas, matchIfMissing=true)` — é o gateway padrão) — integra de verdade com a API do Asaas (`api-sandbox.asaas.com/v3`): cria o cliente, cria a cobrança Pix (com o `agendamentoId` como `externalReference`, para o webhook correlacionar sem mapeamento à parte) e busca o QR Code. `estornar(referenciaExterna, valor)` chama `POST /payments/{id}/refund`. Usa `RestClient` forçado a HTTP/1.1 — o `HttpClient` da JDK tenta negociar HTTP/2 por padrão, o que quebra contra servidores de teste como o WireMock. Config em `config/AsaasProperties` (`@ConfigurationProperties(prefix = "asaas")`).
- **`adapter/out/pagamento/mercadopago/MercadoPagoGatewayAdapter`** (`@Profile("!dev")` + `@ConditionalOnProperty(pagamento.gateway=mercadopago)`) — segundo gateway, ativado setando `PAGAMENTO_GATEWAY=mercadopago`. Integração deliberadamente diferente da do Asaas (documentado como comentário na própria classe): sem "criar cliente" separado, corpo em snake_case (`transaction_amount`, `payment_method_id`...), e expõe `consultarPagamento(id)` (usado pelo webhook, já que o payload do Mercado Pago não inclui status). `estornar(referenciaExterna, valor)` chama `POST /v1/payments/{id}/refunds` com `X-Idempotency-Key`, mesmo padrão de `gerarCobrancaPix`. Config em `config/MercadoPagoProperties` (`@ConfigurationProperties(prefix = "mercadopago")`).
- **`adapter/out/notificacao/email/EmailEnviadorDeNotificacao`** (`@Profile("!dev")`) — envia via SMTP com `JavaMailSender` (`spring-boot-starter-mail`), config em `spring.mail.*`/`notificacao.email.remetente`.
- **`adapter/out/notificacao/twilio/`** (`@Profile("!dev")`) — `TwilioSmsEnviadorDeNotificacao` e `TwilioWhatsAppEnviadorDeNotificacao`, cada um respondendo por um `CanalNotificacao` (`SMS`/`WHATSAPP`). Ambos chamam a mesma Twilio Messages API (`POST /Accounts/{sid}/Messages.json`, corpo form-urlencoded, Basic Auth com `accountSid:authToken`) via `AbstractTwilioEnviadorDeNotificacao` (classe base package-private, não é `@Component` — só as duas subclasses são beans); a única diferença entre os dois é o prefixo `whatsapp:` no `From`/`To`. Números sem código do país (`Contato.telefone` não exige DDI) recebem `+55` automaticamente, já que a API do Twilio exige E.164. Config em `config/TwilioProperties` (`@ConfigurationProperties(prefix = "twilio")`). `NotificacaoEventListener` usa `TwilioWhatsAppEnviadorDeNotificacao`; `TwilioSmsEnviadorDeNotificacao` existe e está testado mas não é acionado por nenhum fluxo (ver `specs/04-roadmap.md`).
- **`adapter/out/calendario/google/GoogleCalendarAdapter`** (`@Profile("!dev")`) — integra com a API real do Google Calendar via conta de serviço (`com.google.auth:google-auth-library-oauth2-http`, sem fluxo OAuth2 interativo — só o e-mail da conta de serviço precisa ser convidado como colaborador do calendário). Chama a API REST direto via `RestClient`, mesmo estilo dos gateways de pagamento (sem SDK pesado do Google). O id do evento no Google é derivado do `agendamentoId` (hex do UUID sem hífens), dispensando mapeamento à parte. Config em `config/GoogleCalendarProperties` (`@ConfigurationProperties(prefix = "google-calendar")`), incluindo `token-server-uri` — configurável para apontar a um WireMock em teste, já que a lib troca o JWT assinado localmente por um access token nesse endpoint.
- **`adapter/out/persistence/memory/`**, `adapter/out/pagamento/memory/GatewayDePagamentoFake`, `adapter/out/evento/PublicadorDeEventosEmMemoria`, `adapter/out/notificacao/memory/EnviadorDeNotificacaoFake`, `adapter/out/clock/SystemClockAdapter` — adapters em memória/fake. Cada um mais seu par `!dev` real implementa as *mesmas* interfaces de `application/port/out` e são mutuamente exclusivos via perfis Spring: `@Profile("dev")` nos de memória/fake, `@Profile("!dev")` nos reais (JPA, `AsaasGatewayAdapter`, `PublicadorDeEventosSpring`, `EmailEnviadorDeNotificacao`) — trocar a tecnologia é só mudança de configuração, nunca de código. Testes de serviço de aplicação também usam os adapters em memória diretamente como dublês de teste (`new InMemoryXxxRepository()`), não mocks, já que são o adapter de verdade, não código exclusivo de teste. `SystemClockAdapter` ainda não tem implementação concorrente (não há por que ter outra), por isso não carrega restrição de `@Profile`. Os dois gateways de pagamento reais usam `@ConditionalOnProperty` além de `@Profile` — é a única situação com *três* implementações concorrentes da mesma porta (`GatewayDePagamentoFake`, `AsaasGatewayAdapter`, `MercadoPagoGatewayAdapter`), então `@Profile` sozinho (dev vs. não-dev) não bastava para decidir entre as duas reais.

## Estratégia de testes

- Testes de domínio: JUnit 5 + AssertJ puro, sem contexto Spring. `AgendamentoTestDataBuilder` constrói o agregado com mais parâmetros de construtor.
- Testes de serviço de aplicação: os adapters em memória de verdade (ver acima) mais um dublê de teste escrito à mão, `ClockFixo` (package-private, vive em `application/service/` nas fontes de teste), para controle determinístico de tempo.
- Testes web: `@WebMvcTest` por controller, casos de uso mockados com `@MockitoBean` (não o `@MockBean`, que está deprecated).
- Testes de persistência: as classes `*RepositoryAdapterIT` estendem `AbstractPersistenceIT` (`@Testcontainers` + um `PostgreSQLContainer` compartilhado + `@DynamicPropertySource` conectando o datasource) — ver a exigência de Docker em Comandos acima.
- Teste dos gateways de pagamento: `AsaasGatewayAdapterTest`/`MercadoPagoGatewayAdapterTest` usam WireMock (dependência `wiremock-standalone`, que embute o Jetty necessário — a variante não-standalone `org.wiremock:wiremock` falha ao subir sem ele) para simular cada API, sem nenhuma chamada real. `MercadoPagoWebhookControllerTest` recalcula o HMAC esperado no próprio teste (mesmo algoritmo do controller) para simular uma assinatura válida — precisa de `@TestPropertySource(properties = "pagamento.gateway=mercadopago")` porque o `@ConditionalOnProperty` do controller não casaria com o padrão (`asaas`) do `application.yml`. Os testes de `estornar(...)` usam `matchingJsonPath("$[?(@.value == 30.00)]")` (predicado JsonPath, não `equalTo` numa string) — o WireMock reformata números ao extrair via JsonPath (`30.00` vira `30.0`), então comparar como string quebra por divergência de formatação, não por bug real; o predicado compara numericamente e evita isso.
- Teste do scheduler: chamada direta ao método do `ExpiracaoReservaScheduler` com o caso de uso mockado, sem depender da infraestrutura de agendamento do Spring.
- Teste do envio de e-mail: `EmailEnviadorDeNotificacaoTest` usa GreenMail (`greenmail-junit5`, servidor SMTP em memória) para verificar o e-mail recebido de verdade, sem mock do `JavaMailSender`.
- Teste dos enviadores Twilio: `TwilioSmsEnviadorDeNotificacaoTest`/`TwilioWhatsAppEnviadorDeNotificacaoTest` usam WireMock, verificando o header `Authorization: Basic ...` e o corpo form-urlencoded (`To`/`From`/`Body`) — inclusive que o prefixo `whatsapp:` e o DDI `+55` automático saem formatados corretamente (comparação via `URLEncoder.encode` no próprio teste, para não errar a mão no percent-encoding esperado).
- `pom.xml` registra o agente byte-buddy do Mockito via goal `properties` do `maven-dependency-plugin` mais `-javaagent` no `argLine` do surefire, seguindo a recomendação do próprio Mockito, para evitar o aviso de depreciação de carregamento dinâmico de agente da JDK.
