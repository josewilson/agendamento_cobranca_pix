## Projeto

Agendamento com cobrança via Pix — uma plataforma de agendamento para prestadores de serviço (clínicas, barbearias, estúdios) com cobrança de sinal/multa de cancelamento via Pix. Projeto de portfólio em arquitetura hexagonal, Java 21 + Spring Boot 3.5.11.

## Regra inegociável: ids e senhas nunca aparecem

Pedido explícito do usuário, vale para toda mudança futura neste projeto, sem exceção:

- **Nenhum id de cadastro (UUID de `Prestador`/`Cliente`/`Servico`/`Agendamento`) pode aparecer como texto visível em nenhuma tela do frontend** — nem em tabela, nem em mensagem de sucesso, nem em "copie este id". Por isso `PrestadoresPage`/`ServicosPage` não têm coluna "Id", `ClientesPage` não mostra o id após cadastrar, e as telas de agendamento não exibem o id como texto. Onde um id é tecnicamente necessário (seleção de prestador/serviço/cliente, navegação), ele vive só como `value` de `<option>` ou parâmetro de rota na URL — nunca como conteúdo renderizado na página. `GET /api/clientes` existe justamente para isso: a tela de novo agendamento usa um `<select>` de clientes (por nome) em vez de pedir pra colar um UUID.
- **Nenhuma senha/credencial real pode subir para o repositório.** Já é assim para toda integração externa — `ASAAS_API_KEY`, `MERCADOPAGO_ACCESS_TOKEN`, `GOOGLE_CALENDAR_CREDENTIALS`, `TWILIO_AUTH_TOKEN`, `SMTP_PASSWORD` — sempre variável de ambiente com valor vazio por padrão em `application.yml`, nunca hardcoded. `frontend/.env` (com a URL da API, nenhum segredo) está no `.gitignore`; só `frontend/.env.example` é versionado. Exceção consciente: `docker-compose.yml`/`application.yml` têm a senha do Postgres local (`agendamento`/`agendamento`) em texto plano — é um container descartável que só existe em `localhost`, não uma credencial real; se isso também precisar sumir do repo, trocar por variável de ambiente é a mesma receita das outras integrações.
- Ao adicionar qualquer tela, endpoint ou integração nova: antes de mostrar algo na UI ou de commitar uma config, pare e pergunte "isso é um id de cadastro ou uma senha/token?" — se for, não aparece na tela e não vai pro git.
- Vale também para a senha de login do `Prestador` (`adapter/in/web/security/`): nunca armazenada/retornada em texto puro — só o hash BCrypt (`Prestador.senhaHash()`), gerado por `PasswordEncoder` na aplicação (nunca no domínio). `PrestadorResponse` nunca inclui `senhaHash`; o frontend só envia a senha (HTTPS em produção faria isso valer de verdade — em dev, `localhost`) e nunca a lê de volta.

## Comandos

Não há `mvn` nem Maven wrapper (`mvnw`) no PATH deste ambiente, e `.mvn/` não tem o jar do wrapper. **Mas existe um Maven de verdade bundlado com o IntelliJ**, utilizável via Bash:
`"/c/Users/jwaso/AppData/Local/Programs/IntelliJ IDEA/plugins/maven-plugin/lib/maven3/bin/mvn.cmd"` (ou o path Windows equivalente) — `mvn compile`, `mvn test`, `mvn -Dtest=NomeDaClasse#metodo test`, `mvn spring-boot:run` funcionam normalmente. Achado nesta sessão depois que `pom.xml` ganhou uma dependência nova (`spring-boot-starter-security`) e nem `mcp__idea__build_project` nem `mcp__idea__execute_run_configuration` pegavam o jar novo — o projeto do IntelliJ só reimporta o Maven via UI (clique em "Load Maven Changes"), que as ferramentas MCP não conseguem disparar. **Sempre que `pom.xml` mudar nesta sessão, rode esse `mvn` real em vez de `mcp__idea__build_project`/`execute_run_configuration`** — essas ferramentas continuam ótimas para builds/testes que não mexem em dependências. Use `-o` (offline) depois da primeira chamada sem `-o` para cada dependência nova (ela precisa baixar do Maven Central uma vez).

- Build/compilar: `mcp__idea__build_project` (sem mudança de dependência) ou `mvn compile`/`mvn test-compile` (bundlado, após mudança em `pom.xml`). Passe `rebuild: true` no primeiro se um build incremental reportar sucesso mas um teste ainda falhar numa classe desatualizada — isso já aconteceu depois de editar um arquivo do qual muitos outros dependem (ex.: adicionar `@Profile` em vários adapters de uma vez).
- Rodar uma classe ou método de teste isolado: `mcp__idea__get_run_configurations` com `filePath` para obter a linha da classe/método, depois `mcp__idea__execute_run_configuration` com esse `filePath` + `line` — ou `mvn -Dtest=NomeDaClasse#metodo test` com o Maven bundlado.
- Rodar a aplicação real sem passar pelo run configuration do IntelliJ (útil logo após mudar `pom.xml`, quando o run configuration ainda aponta pra classes desatualizadas do projeto do IDE): `mvn spring-boot:run` com o Maven bundlado, em background — sobe em `localhost:8080` igual ao run configuration normal.

### Rodando a aplicação / testes de integração localmente

- `docker-compose up -d` sobe a instância do Postgres que o perfil Spring padrão precisa (configuração do datasource em `src/main/resources/application.yml`; o schema vem das migrations Flyway em `src/main/resources/db/migration`, validadas contra as entidades JPA na subida via `spring.jpa.hibernate.ddl-auto=validate`).
- As classes `*RepositoryAdapterIT` em `adapter/out/persistence/jpa` usam Testcontainers (um container Postgres descartável, independente do docker-compose) — o Docker Desktop precisa estar rodando ou elas falham ao subir o container. Os bugs antigos de isolamento/comparação de `Instant`/`BigDecimal` foram corrigidos (ver `specs/04-roadmap.md`). **Atenção**: nesta máquina, rodar as 4 classes juntas no mesmo fork Maven às vezes falha com `CannotCreateTransaction`/conexão recusada (limitação de recursos locais, múltiplos contextos Spring + Testcontainers em sequência) — rode cada classe sozinha (`mvn -Dtest=NomeDaClasse test`) se isso acontecer; não é bug do código. O CI (`.github/workflows/ci.yml`) roda todas juntas sem esse problema.
- **O perfil Spring `dev` é de uso exclusivo dos testes** (troca todos os adapters de persistência/pagamento/notificação/calendário pelos em memória/fake — ver Arquitetura abaixo). **Nunca use `dev` para rodar ou demonstrar a aplicação de verdade** — isso sempre deve ser feito com `docker-compose up -d` + perfil padrão (Postgres real), confirmado funcionando (Flyway migra as 4 tabelas, todos os adapters `!dev` sobem mesmo sem credenciais configuradas). Um documento de perfil dedicado em `application.yml` (`spring.config.activate.on-profile: dev`) exclui `HibernateJpaAutoConfiguration`/`DataSourceAutoConfiguration`/`DataSourceTransactionManagerAutoConfiguration`/`FlywayAutoConfiguration` só para esse perfil de teste — sem isso a aplicação ainda tentaria abrir uma conexão JDBC no startup mesmo sem nenhum repositório JPA em uso.
- `DevDataSeeder` (`adapter/in/seed/`, `@Profile("dev")`) popula um prestador/cliente/serviço de IDs fixos (`00000000-...-0001/0002/0003`) no startup — um atalho rápido pro perfil de teste. Fora dele, use os endpoints de cadastro reais: `POST /api/prestadores`, `POST /api/clientes`, `POST /api/servicos` (ver `specs/03-api-rest.md`).
- Integração real com o Asaas exige `ASAAS_API_KEY` e `ASAAS_WEBHOOK_TOKEN`, com o Mercado Pago exige `MERCADOPAGO_ACCESS_TOKEN` e `MERCADOPAGO_WEBHOOK_SECRET`, com o Google Calendar exige `GOOGLE_CALENDAR_CREDENTIALS` (JSON da conta de serviço) e `GOOGLE_CALENDAR_ID`, com o Twilio (SMS/WhatsApp) exige `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_SMS_FROM` (variáveis de ambiente); sem elas a aplicação sobe normalmente (perfil padrão), só não consegue emitir cobranças/sincronizar agenda/enviar SMS-WhatsApp de verdade. Qual gateway de pagamento está ativo é `PAGAMENTO_GATEWAY` (`asaas`, o padrão, ou `mercadopago`) — ver Arquitetura abaixo.

### Docker / CI

- `Dockerfile` (multi-estágio: build com Maven, imagem final só com o jar numa JRE Alpine) builda a aplicação real — `docker build -t agendamento-com-cobranca-pix .`. `docker-compose.yml` ganhou o serviço `app` além do `postgres`: `docker-compose up -d` sobe os dois juntos (healthcheck no Postgres antes de subir a aplicação), com `SPRING_DATASOURCE_*` apontando pro serviço `postgres` via binding relaxado do Spring Boot (nenhum `application.yml` extra precisa existir pra isso). Pra subir só o Postgres (uso local de desenvolvimento, aplicação rodando fora do Docker) continue usando `docker-compose up -d postgres`.
- `.github/workflows/ci.yml` roda a suíte Java inteira (`mvn test`, inclusive `ArchitectureTest` e os `*RepositoryAdapterIT` — o runner do GitHub Actions já tem Docker, sem a limitação de recursos da máquina local) + build da imagem Docker, e builda o frontend (`npm ci && npm run build`) num job separado.

### Frontend (`frontend/`)

Projeto React + Vite + JavaScript puro + CSS puro, **completamente separado do backend** (próprio `package.json`, próprio dev server, zero código compartilhado) — conversa só via REST/CORS. Dá pra executar o fluxo inteiro do projeto numa tela: cadastrar prestador (com login), fazer login, cadastrar serviço e cliente, criar um agendamento, simular o pagamento (webhook genérico), cancelar, marcar no-show, ver a própria agenda.

- Rodar: `cd frontend && npm install && npm run dev` — sobe em `http://localhost:5173`. Precisa do backend rodando em `http://localhost:8080` (`docker-compose up -d` + `AgendamentoApplication`, perfil padrão) com CORS liberado para essa origem (já é o padrão em `application.yml`, `app.cors.allowed-origins`).
- `src/api/client.js` é o único ponto que fala com a API (`fetch` nativo, sem axios) — lê a URL base de `VITE_API_BASE_URL` (`.env`, padrão `http://localhost:8080`) e já traduz `ErrorResponse.mensagem` do backend em exceções JS. Todo request vai com `credentials: 'include'` — necessário pro cookie de sessão do login ser enviado de volta (origem diferente do backend), e exige `allowCredentials(true)` no CORS do backend (já configurado).
- `src/auth/AuthContext.jsx` guarda o estado de login (`{ prestadorId, nome }` vindo de `GET /api/auth/me`, verificado uma vez no mount via `AuthProvider`) e expõe `login`/`logout`. `src/auth/RequireAuth.jsx` protege rota (`/agenda`, `/servicos`) redirecionando pra `/login` quando deslogado. `prestadorId` fica só em estado JS, nunca renderizado como texto (mesma regra de sempre) — existe só pra telas que precisam montar uma URL de API com ele (`ServicosPage` listando os próprios serviços); cadastro de serviço nem precisa dele, o backend deriva da sessão.
- Prestador (listagem pública)/serviço/cliente são sempre escolhidos por `<select>` (nome, não id) — `GET /api/clientes` existe só pra isso. Nenhuma tela mostra um id como texto (ver "Regra inegociável" acima).
- `npm audit` acusa vulnerabilidades moderadas em `esbuild`/`vite` (exposição do dev server) e `react-router` (bypass de redirect; o aviso de hidratação SSR não se aplica — este projeto não usa SSR). Corrigir exige major bumps (`vite@8`, `react-router-dom@7`) — ver `specs/04-roadmap.md`.

## Arquitetura

Hexagonal (portas e adapters), garantida por `src/test/java/.../architecture/ArchitectureTest.java` (ArchUnit): domínio não pode depender de Spring, JPA, nem de `adapter.*`; aplicação não pode depender de `adapter.*` nem de JPA; sem ciclos de pacotes entre `domain`/`application`/`adapter`.

- **`domain/`** — Java puro, zero imports de framework. `model/` tem as entidades (`Agendamento`, `Cliente`, `Prestador`, `Servico` — mutáveis, igualdade por identidade; `Cliente.atualizarDadosCadastrais(...)`, `Prestador.atualizarPerfil(...)` e `Servico.atualizarDados(...)` editam campos de cadastro mantendo id/documento/identidade intactos, ver `01-dominio.md` e `03-api-rest.md` pros endpoints `PUT`) e os value objects (`Periodo`, `Dinheiro`, `Contato`, `DocumentoFiscal`, `PoliticaCancelamento` — `record`s com construtores compactos que validam). `domain/model/shared/FormatoContato` centraliza a validação de formato de email/telefone usada tanto por `Contato` quanto por `Prestador` (que não reaproveita o VO `Contato` em si — telefone de prestador é um campo isolado, sem o par email+telefone que `Contato` representa). O switch `transicoesValidas()` de `StatusAgendamento` é a única fonte de verdade da máquina de estados do agendamento. `service/VerificadorDeConflito` é o único domain service (checagem de conflito de horário). `event/` tem uma `sealed interface EventoDeDominio` e suas implementações em `record`.
  - `Agendamento.criar(...)` é o único jeito de criar um agendamento *novo* — valida "não no passado" e deriva o status inicial de se há sinal devido. `Agendamento.reconstituir(...)` é o caminho separado que os adapters de persistência usam para reidratar uma linha do banco sem reaplicar essa validação de criação (um agendamento histórico, já concluído, precisa carregar mesmo com o período no passado).
  - `referenciaPagamento` (nullable, `Optional<String>` no getter) guarda o id da cobrança no gateway de pagamento, vinculado uma única vez via `vincularReferenciaPagamento(String)` — necessário para o `EstornoEventListener` saber o que estornar no cancelamento. `null`/vazio para agendamentos que nunca exigiram sinal.
  - Valor monetário é sempre `Dinheiro` (envolve `BigDecimal`, escala normalizada para 2 via `HALF_EVEN` no construtor compacto) — nunca `double`/`float`.
- **`application/`** — orquestração dos casos de uso. `port/in` tem uma interface + um `record` de Command/Query por caso de uso (criar, confirmar, cancelar, marcar no-show, expirar reservas pendentes, processar webhook de pagamento, consultar por id). `port/out` tem uma interface de repositório por agregado, mais `GatewayDePagamento`, `PublicadorDeEventos` e `Clock` (abstrai `Instant.now()` para as regras sensíveis a tempo serem testáveis deterministicamente). `service/*Service` implementam as portas `in` como beans `@Service` — aplicação *pode* depender de Spring, só `domain` é livre de framework. `ProcessarWebhookPagamentoService` só delega para `ConfirmarAgendamentoUseCase`; propositalmente não há outro jeito de confirmar um agendamento (nenhum endpoint REST manual de "confirmar").
- **`adapter/in/web/`** — controllers REST + um DTO por request/response + `GlobalExceptionHandler` mapeando exceções de domínio/aplicação para status HTTP (404 `RecursoNaoEncontradoException`, 403 `AcessoNaoAutorizadoException` — prestador autenticado tentando editar/excluir recurso de outro —, 409 `ConflitoDeHorarioException`/`TransicaoDeStatusInvalidaException`/`DataIntegrityViolationException` — constraint única ou estrangeira do banco, mensagem genérica de propósito —, 400 falhas de bean validation e `IllegalArgumentException`/`IllegalStateException`). `AsaasWebhookController` (`POST /api/webhooks/asaas`) traduz o payload real do Asaas para `WebhookPagamentoCommand`, validando o header `asaas-access-token` antes de processar qualquer evento. `MercadoPagoWebhookController` (`POST /api/webhooks/mercadopago`) faz o mesmo para o Mercado Pago, mas o payload de lá só traz o id do pagamento (não o status) — o controller consulta de volta via `MercadoPagoGatewayAdapter.consultarPagamento(id)` e valida a assinatura HMAC-SHA256 no header `x-signature` em vez de um token simples. Os dois webhooks (e os dois gateways de pagamento — ver abaixo) só ficam ativos conforme a propriedade `pagamento.gateway` (`@ConditionalOnProperty`); nenhum código muda para trocar de gateway, só essa propriedade.
  - `PrestadorController` (`POST`/`GET`/`PUT /{id} /api/prestadores`), `ClienteController` (`POST`/`GET`/`PUT /{id}`/`DELETE /{id} /api/clientes`) e `ServicoController` (`POST`/`PUT /{id}`/`DELETE /{id} /api/servicos`, `GET /api/servicos?prestadorId=`) seguem exatamente o mesmo estilo de `AgendamentoController` — cada um com seu caso de uso em `application/port/in`+`application/service` (`CadastrarPrestadorUseCase`, `AtualizarPrestadorUseCase`, etc.), DTOs com `static de(...)` para mapear domínio→resposta. `PrestadorRepository.buscarTodos()`/`buscarPorEmail(String)`, `ServicoRepository.buscarPorPrestador(PrestadorId)`/`excluir(ServicoId)` e `ClienteRepository.excluir(ClienteId)` são extensões dos ports (implementadas tanto em memória quanto via JPA). `AgendamentoController` ganhou `GET /api/agendamentos` (sem path variable, distinto de `GET /api/agendamentos/{id}`) — lista a agenda do prestador autenticado, ver `ListarAgendamentosPorPrestadorUseCase` em `specs/02-casos-de-uso.md`. Os `Atualizar*`/`Excluir*` de `Servico`/`Prestador` verificam que o recurso pertence ao prestador autenticado antes de agir, lançando `AcessoNaoAutorizadoException` (403) se não bater — `Cliente` continua sem essa checagem, consistente com não ter login.
  - **`adapter/in/web/security/`** — login simples de Prestador (sessão via cookie, Spring Security), pedido explícito do usuário com escopo deliberadamente restrito: só `Prestador` autentica; `Cliente` continua sem login, e o fluxo público de reserva (listar prestador/serviço, cadastrar cliente, criar/consultar/cancelar/marcar no-show um agendamento, webhooks de pagamento) fica liberado sem autenticação — só a área de gestão do próprio prestador (`GET /api/agendamentos`, `POST`/`PUT`/`DELETE /api/servicos`, `PUT /api/prestadores/{id}`) exige login. `Prestador` ganhou `email` (único) e `senhaHash` (BCrypt, nunca exposto em `PrestadorResponse`) — `CadastrarPrestadorService` injeta `PasswordEncoder` para gerar o hash a partir da senha em texto puro do `CadastrarPrestadorCommand`, o domínio nunca faz hashing (ia depender de Spring Security, o que violaria "domínio não pode depender de Spring"). `PrestadorPrincipal implements UserDetails` (envolve `Prestador`) + `PrestadorUserDetailsService implements UserDetailsService` (busca por email via `PrestadorRepository`) — controllers protegidos usam `@AuthenticationPrincipal PrestadorPrincipal` para pegar o `PrestadorId` da sessão em vez de confiar num valor enviado pelo cliente.
    - `SecurityConfig` (`@EnableWebSecurity`) é o **único lugar que configura CORS** (`CorsConfigurationSource` próprio a partir de `config/CorsProperties`, `@EnableConfigurationProperties(CorsProperties.class)` na própria classe) — `WebConfig` (que antes também configurava CORS, via `WebMvcConfigurer`) foi **removido**: as duas configs duplicavam a mesma lista de origens/métodos (achado de uma auditoria de código), e `WebConfig` nunca era, de fato, quem decidia CORS em produção (o Security governa toda a cadeia de filtros de qualquer forma). Não dá pra confiar só na integração automática do Spring Security com o `HandlerMappingIntrospector` do Spring MVC (`.cors(withDefaults())` sozinho, sem um `CorsConfigurationSource` bean próprio) porque os testes de persistência (`*RepositoryAdapterIT`) sobem o contexto com `web-application-type=none`, sem MVC nenhum, e isso falhava com `NoSuchBeanDefinitionException`.
    - **CSRF habilitado** via `CookieCsrfTokenRepository.withHttpOnlyFalse()` + `CsrfTokenRequestAttributeHandler`, exceto para `/api/webhooks/**` (Asaas/Mercado Pago chamam sem navegador nem cookie de sessão; autenticidade já garantida por token/assinatura nos próprios controllers). `CsrfCookieFilter` força o cookie `XSRF-TOKEN` a ser gravado em toda requisição (inclusive `GET`) — sem ele o Spring Security só grava o cookie na primeira vez que algo lê o token, o que nunca aconteceria sozinho numa API sem views server-side. O frontend lê o cookie e reenvia como header `X-XSRF-TOKEN` em toda chamada não-`GET` (`frontend/src/api/client.js`).
    - `/error` e `/actuator/health` estão em `permitAll` de propósito: sem o primeiro, uma exceção não tratada (e portanto um status 500 de verdade) viraria um 401 enganoso, porque o redespacho interno do Tomcat pro `/error` passa pelo filtro de novo e esbarra em `anyRequest().authenticated()`; sem o segundo, um orquestrador não autenticado não conseguiria checar a saúde da aplicação.
    - `AuthController` faz login/logout/`me` (`POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`) sem usar o `formLogin()`/`httpBasic()` padrão do Spring Security (pensados pra formulário HTML/popup do browser, não pra uma API JSON) — autentica explicitamente via `AuthenticationManager` e grava o `SecurityContext` na sessão via `HttpSessionSecurityContextRepository`, mesmo mecanismo que o filtro padrão usaria, só disparado manualmente pra controlar o formato da resposta.
    - `LoginRateLimiter` (mesmo pacote) bloqueia por 5 minutos um email que falhar o login 5 vezes seguidas (em memória, `ConcurrentHashMap` por email normalizado — não por IP; não compartilhado entre réplicas num deploy com mais de uma instância, ver `specs/04-roadmap.md`), usando a porta `Clock` já existente (a mesma do domínio) pra ser testável deterministicamente. `AuthController.login` consulta `bloqueado(email)` antes de chamar o `AuthenticationManager`; se bloqueado, lança `LoginBloqueadoException` (429 via `GlobalExceptionHandler`). Achado de auditoria de segurança (02/10/2026): sem isso, `/api/auth/login` não tinha nenhum limite de tentativas.
    - As duas comparações de segredo do fluxo de webhook (`AsaasWebhookController`, token do header `asaas-access-token`; `MercadoPagoWebhookController`, assinatura HMAC-SHA256 do header `x-signature`) usam `MessageDigest.isEqual(...)` em vez de `Objects.equals`/`String.equals` — comparação em tempo constante, pra não vazar via timing quantos bytes do segredo o chamador acertou (achado de auditoria de segurança, 02/10/2026, mais relevante no caso do Mercado Pago por ser uma assinatura criptográfica recalculada).
    - **Cada `@WebMvcTest` do projeto precisa de `@Import(SecurityConfig.class)`** — sem isso a fatia de teste cai no `SecurityFilterChain` padrão auto-configurado do Spring Boot (CSRF habilitado com token aleatório que o teste não tem como fornecer, tudo exige login), não no `SecurityFilterChain` de verdade do projeto; mesma causa raiz do problema do `CorsProperties` (plain `@Configuration` não é um dos estereótipos que `@WebMvcTest` inclui automaticamente). Testes que batem em endpoint protegido autenticam via `SecurityMockMvcRequestPostProcessors.authentication(...)` — helper compartilhado em `TestAutenticacao` (fonte de teste, mesmo pacote) — e qualquer `POST`/`PUT`/`DELETE` precisa de `.with(SecurityMockMvcRequestPostProcessors.csrf())` além disso, senão o CSRF do teste falha antes de chegar no controller.
- **`spring-boot-starter-actuator`** expõe `/actuator/health` e `/actuator/prometheus` (`management.endpoints.web.exposure.include: health,prometheus`, `show-details: never` — os demais endpoints do Actuator vazam detalhe de implementação sem necessidade; os dois expostos são `permitAll` em `SecurityConfig`, infraestrutura de monitoramento, não dado de negócio). `micrometer-registry-prometheus` no `pom.xml` habilita o segundo. `management.health.mail.enabled: false` porque `spring-boot-starter-mail` registra um health check que tenta conectar no SMTP configurado — mas email é integração opcional aqui (a aplicação sobe e funciona sem SMTP configurado), então um SMTP fora do ar não deveria derrubar o `/health` da aplicação inteira (achado testando o container Docker).
- **`config/AsyncConfig`** (`@EnableAsync` + bean `eventosExecutor`, um `ThreadPoolTaskExecutor` dedicado, separado do pool HTTP do Tomcat de propósito) — os 7 métodos `@EventListener` de `NotificacaoEventListener`/`CalendarioEventListener`/`EstornoEventListener` (ver abaixo) rodam com `@Async("eventosExecutor")`. Sem isso, `ApplicationEventPublisher.publishEvent` (síncrono por padrão) faria o I/O de SMTP/Twilio/Google Calendar/gateway de pagamento bloquear a thread da requisição HTTP que publicou o evento (achado de auditoria de performance, 02/10/2026). Os testes desses listeners chamam os métodos diretamente, sem contexto Spring, então não passam pelo proxy `@Async` e continuam síncronos/determinísticos.
- **`adapter/in/scheduler/`** — `ExpiracaoReservaScheduler`, um `@Scheduled` que aciona `ExpirarReservasPendentesUseCase` periodicamente (intervalo em `agendamento.expiracao.intervalo-ms`, padrão 60s). Usa `initialDelay` igual ao `fixedDelay` de propósito — sem isso, `@Scheduled` dispara a primeira execução no instante em que o contexto Spring sobe, o que rodaria em todo teste que carrega o contexto completo.
- **`adapter/in/evento/NotificacaoEventListener`** — `@EventListener` para `AgendamentoCriado`/`AgendamentoConfirmado`/`AgendamentoCancelado`; busca o `Cliente` pelo `clienteId` do evento e dispara **dois canais** via `NotificacaoDispatcher` (application/service — roteia por `CanalNotificacao` para o `EnviadorDeNotificacao` certo): `EMAIL` (registro formal) e `WHATSAPP` (canal que o cliente brasileiro de fato confere para esse tipo de aviso). Cada canal é enviado num try/catch isolado (`enviarPorCanal`) — a falha de um (ex.: Twilio fora do ar) não impede o outro nem propaga para o caso de uso que já persistiu o agendamento. `SMS` tem adapter pronto mas não é usado (dois canais já bastam, ver `specs/04-roadmap.md`). Só funciona porque `PublicadorDeEventosSpring` (`@Profile("!dev")`) delega ao `ApplicationEventPublisher` do Spring — os eventos de domínio continuam sendo `record`s puros, só esse adapter conhece Spring.
- **`adapter/in/evento/CalendarioEventListener`** — mesmo padrão do `NotificacaoEventListener`, mas só reage a `AgendamentoConfirmado` (cria o evento externo) e `AgendamentoCancelado` (remove); propositalmente ignora `AgendamentoCriado`, já que um agendamento `PENDENTE_PAGAMENTO` pode expirar sem nunca ocupar a agenda de verdade. Delega para `CalendarioExternoPort`.
- **`adapter/in/evento/EstornoEventListener`** — mesmo padrão de novo: reage a `AgendamentoCancelado`, só age quando `resultado.valorReembolsado() > 0`, busca o `Agendamento` para pegar `referenciaPagamento()` (vazio quando o agendamento nunca teve sinal) e chama `GatewayDePagamento.estornar(referencia, valor)`. Falha logada, nunca propagada.
- **`adapter/out/persistence/jpa/`** — adapters reais para Postgres. As classes de `entity/` são POJOs JPA `@Entity` planos (sem tipos de domínio, sem embeddables) com construtor sem argumentos **público** — precisa ser público porque `mapper/` está num pacote irmão, não no mesmo, então `protected` não seria alcançável de lá. As classes de `mapper/` fazem toda a tradução domínio↔JPA, inclusive reconstruindo os value objects (o que reexecuta a validação deles a cada carregamento). `repository/` são interfaces `JpaRepository` simples; as classes `*RepositoryAdapter` as envolvem e implementam as interfaces de `application/port/out`.
- **`adapter/out/pagamento/asaas/AsaasGatewayAdapter`** (`@Profile("!dev")` + `@ConditionalOnProperty(pagamento.gateway=asaas, matchIfMissing=true)` — é o gateway padrão) — integra de verdade com a API do Asaas (`api-sandbox.asaas.com/v3`): cria o cliente, cria a cobrança Pix (com o `agendamentoId` como `externalReference`, para o webhook correlacionar sem mapeamento à parte) e busca o QR Code. `estornar(referenciaExterna, valor)` chama `POST /payments/{id}/refund`. Usa `RestClient` forçado a HTTP/1.1 — o `HttpClient` da JDK tenta negociar HTTP/2 por padrão, o que quebra contra servidores de teste como o WireMock. Config em `config/AsaasProperties` (`@ConfigurationProperties(prefix = "asaas")`). `HttpClient.connectTimeout` (5s) + `JdkClientHttpRequestFactory.setReadTimeout` (10s) configurados — achado de auditoria de performance (02/10/2026): sem timeout, uma API externa travada prenderia a thread chamadora indefinidamente. Mesmo tratamento nos outros 3 adapters HTTP abaixo (Mercado Pago, Google Calendar, Twilio).
- **`adapter/out/pagamento/mercadopago/MercadoPagoGatewayAdapter`** (`@Profile("!dev")` + `@ConditionalOnProperty(pagamento.gateway=mercadopago)`) — segundo gateway, ativado setando `PAGAMENTO_GATEWAY=mercadopago`. Integração deliberadamente diferente da do Asaas (documentado como comentário na própria classe): sem "criar cliente" separado, corpo em snake_case (`transaction_amount`, `payment_method_id`...), e expõe `consultarPagamento(id)` (usado pelo webhook, já que o payload do Mercado Pago não inclui status). `estornar(referenciaExterna, valor)` chama `POST /v1/payments/{id}/refunds` com `X-Idempotency-Key`, mesmo padrão de `gerarCobrancaPix`. Config em `config/MercadoPagoProperties` (`@ConfigurationProperties(prefix = "mercadopago")`).
- **`adapter/out/notificacao/email/EmailEnviadorDeNotificacao`** (`@Profile("!dev")`) — envia via SMTP com `JavaMailSender` (`spring-boot-starter-mail`), config em `spring.mail.*`/`notificacao.email.remetente`.
- **`adapter/out/notificacao/twilio/`** (`@Profile("!dev")`) — `TwilioSmsEnviadorDeNotificacao` e `TwilioWhatsAppEnviadorDeNotificacao`, cada um respondendo por um `CanalNotificacao` (`SMS`/`WHATSAPP`). Ambos chamam a mesma Twilio Messages API (`POST /Accounts/{sid}/Messages.json`, corpo form-urlencoded, Basic Auth com `accountSid:authToken`) via `AbstractTwilioEnviadorDeNotificacao` (classe base package-private, não é `@Component` — só as duas subclasses são beans); a única diferença entre os dois é o prefixo `whatsapp:` no `From`/`To`. Números sem código do país (`Contato.telefone` não exige DDI) recebem `+55` automaticamente, já que a API do Twilio exige E.164. Config em `config/TwilioProperties` (`@ConfigurationProperties(prefix = "twilio")`). `NotificacaoEventListener` usa `TwilioWhatsAppEnviadorDeNotificacao`; `TwilioSmsEnviadorDeNotificacao` existe e está testado mas não é acionado por nenhum fluxo (ver `specs/04-roadmap.md`).
- **`adapter/out/calendario/google/GoogleCalendarAdapter`** (`@Profile("!dev")`) — integra com a API real do Google Calendar via conta de serviço (`com.google.auth:google-auth-library-oauth2-http`, sem fluxo OAuth2 interativo — só o e-mail da conta de serviço precisa ser convidado como colaborador do calendário). Chama a API REST direto via `RestClient`, mesmo estilo dos gateways de pagamento (sem SDK pesado do Google). O id do evento no Google é derivado do `agendamentoId` (hex do UUID sem hífens), dispensando mapeamento à parte. Config em `config/GoogleCalendarProperties` (`@ConfigurationProperties(prefix = "google-calendar")`), incluindo `token-server-uri` — configurável para apontar a um WireMock em teste, já que a lib troca o JWT assinado localmente por um access token nesse endpoint.
- **`adapter/out/persistence/memory/`**, `adapter/out/pagamento/memory/GatewayDePagamentoFake`, `adapter/out/evento/PublicadorDeEventosEmMemoria`, `adapter/out/notificacao/memory/EnviadorDeNotificacaoFake`, `adapter/out/clock/SystemClockAdapter` — adapters em memória/fake. Cada um mais seu par `!dev` real implementa as *mesmas* interfaces de `application/port/out` e são mutuamente exclusivos via perfis Spring: `@Profile("dev")` nos de memória/fake, `@Profile("!dev")` nos reais (JPA, `AsaasGatewayAdapter`, `PublicadorDeEventosSpring`, `EmailEnviadorDeNotificacao`) — trocar a tecnologia é só mudança de configuração, nunca de código. Testes de serviço de aplicação também usam os adapters em memória diretamente como dublês de teste (`new InMemoryXxxRepository()`), não mocks, já que são o adapter de verdade, não código exclusivo de teste. `SystemClockAdapter` ainda não tem implementação concorrente (não há por que ter outra), por isso não carrega restrição de `@Profile`. Os dois gateways de pagamento reais usam `@ConditionalOnProperty` além de `@Profile` — é a única situação com *três* implementações concorrentes da mesma porta (`GatewayDePagamentoFake`, `AsaasGatewayAdapter`, `MercadoPagoGatewayAdapter`), então `@Profile` sozinho (dev vs. não-dev) não bastava para decidir entre as duas reais.

## Estratégia de testes

- Testes de domínio: JUnit 5 + AssertJ puro, sem contexto Spring. `AgendamentoTestDataBuilder` constrói o agregado com mais parâmetros de construtor.
- Testes de serviço de aplicação: os adapters em memória de verdade (ver acima) mais um dublê de teste escrito à mão, `ClockFixo` (package-private, vive em `application/service/` nas fontes de teste), para controle determinístico de tempo.
- Testes web: `@WebMvcTest` por controller, casos de uso mockados com `@MockitoBean` (não o `@MockBean`, que está deprecated).
- Testes de persistência: as classes `*RepositoryAdapterIT` estendem `AbstractPersistenceIT` (`@Testcontainers` + um `PostgreSQLContainer` compartilhado + `@DynamicPropertySource` conectando o datasource + `@Transactional` — rollback automático por método, evitando que o `Prestador`/`Cliente` de documento fixo inserido no `setUp()` de um teste colida com a constraint única no próximo teste da mesma classe) — ver a exigência de Docker em Comandos acima. Comparação de `Instant` usa `isCloseTo(..., within(1, ChronoUnit.MILLIS))`, não igualdade exata nem truncamento pra microssegundo — o round-trip via driver JDBC pode introduzir um resíduo sub-microssegundo que não bate com um truncamento limpo. Comparação de `BigDecimal` (direto ou dentro de um record como `PoliticaCancelamento`) usa `isEqualByComparingTo`/campo a campo, nunca `equals()`/comparação do record inteiro — `numeric` do Postgres volta com escala diferente (`100.00` vs `100` em memória).
- Testes de controller autenticado: `TestAutenticacao.doPrestador(prestadorId)` (`adapter/in/web/security/`, fonte de teste) constrói a `Authentication` pra usar com `SecurityMockMvcRequestPostProcessors.authentication(...)` — helper compartilhado entre `AgendamentoControllerTest`, `ServicoControllerTest` e `PrestadorControllerTest`, não precisa de `PrestadorUserDetailsService`/`PrestadorRepository` de verdade.
- `LoginRateLimiterTest` testa a lógica de bloqueio isoladamente (um `Clock` fake local na classe, não o `ClockFixo` package-private de `application/service`, que não é acessível de `adapter/in/web/security`). `AuthControllerTest` (`@WebMvcTest` + `@Import(SecurityConfig.class)`, como todos) mocka `AuthenticationManager`/`LoginRateLimiter` — nesse teste foi confirmado que uma `AuthenticationException` lançada dentro do método do controller (não do filtro) já vira 401 (o `ExceptionTranslationFilter` do Spring Security intercepta mesmo assim), não um 500 cru.
- Teste dos gateways de pagamento: `AsaasGatewayAdapterTest`/`MercadoPagoGatewayAdapterTest` usam WireMock (dependência `wiremock-standalone`, que embute o Jetty necessário — a variante não-standalone `org.wiremock:wiremock` falha ao subir sem ele) para simular cada API, sem nenhuma chamada real. `MercadoPagoWebhookControllerTest` recalcula o HMAC esperado no próprio teste (mesmo algoritmo do controller) para simular uma assinatura válida — precisa de `@TestPropertySource(properties = "pagamento.gateway=mercadopago")` porque o `@ConditionalOnProperty` do controller não casaria com o padrão (`asaas`) do `application.yml`. Os testes de `estornar(...)` usam `matchingJsonPath("$[?(@.value == 30.00)]")` (predicado JsonPath, não `equalTo` numa string) — o WireMock reformata números ao extrair via JsonPath (`30.00` vira `30.0`), então comparar como string quebra por divergência de formatação, não por bug real; o predicado compara numericamente e evita isso.
- Teste do scheduler: chamada direta ao método do `ExpiracaoReservaScheduler` com o caso de uso mockado, sem depender da infraestrutura de agendamento do Spring.
- Teste do envio de e-mail: `EmailEnviadorDeNotificacaoTest` usa GreenMail (`greenmail-junit5`, servidor SMTP em memória) para verificar o e-mail recebido de verdade, sem mock do `JavaMailSender`.
- Teste dos enviadores Twilio: `TwilioSmsEnviadorDeNotificacaoTest`/`TwilioWhatsAppEnviadorDeNotificacaoTest` usam WireMock, verificando o header `Authorization: Basic ...` e o corpo form-urlencoded (`To`/`From`/`Body`) — inclusive que o prefixo `whatsapp:` e o DDI `+55` automático saem formatados corretamente (comparação via `URLEncoder.encode` no próprio teste, para não errar a mão no percent-encoding esperado).
- `pom.xml` registra o agente byte-buddy do Mockito via goal `properties` do `maven-dependency-plugin` mais `-javaagent` no `argLine` do surefire, seguindo a recomendação do próprio Mockito, para evitar o aviso de depreciação de carregamento dinâmico de agente da JDK.
